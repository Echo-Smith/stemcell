# 错误率告警改造记录

## 使用的模型与工具

- 模型：OpenAI Codex（GPT-5）。
- 文档核对：Context7（前序实现阶段用于核对 Node.js 运行时接口）。
- 实现与验证：Node.js 22.23.2、TypeScript 5.9.3、Node.js 内置 `node:test`、ZIP/只读目录验收脚本。
- 未使用 Claude Code、Cursor 或外部 API；运行时仍为零第三方依赖。

## 关键迭代记录

1. 先读取原有契约、诊断策略和 25 项回归测试，确定新增能力应位于独立 DiagnosisPolicy，而不是 HTTP 工具层。
2. 先增加定向测试，再运行旧构建：21 项中 16 项通过、5 项失败。失败点分别是默认值缺失、严格校验拒绝新字段，以及三类聚合告警行为缺失。
3. 在类型契约和运行时校验中加入可选输入策略，并归一化为默认值 `0.5`。
4. 在所有原有逐服务诊断完成后追加错误率判断，不改写、不替换、不重排原诊断。
5. 更新 README、JSONL 协议和 evaluation 用例，并执行完整回归、逐行评估及 Node.js 22 只读 ZIP 验收。

## 关键取舍

- 使用 `unhealthy / total` 作为错误率，与题目定义完全一致；`degraded` 不计入不可用服务。
- 比较符使用 `>=`，明确覆盖“达到或超过”阈值。
- `HIGH_ERROR_RATE` 仅追加，不参与服务状态和 `overall_status` 计算，避免影响原有能力。
- 聚合证据包含每个不健康服务的每次尝试，而不是只取最后一次，保留重试过程证据。
- 阈值允许 0 和 1；但没有任何不健康服务时不产生告警，避免阈值为 0 时同时出现 `NO_ACTION_REQUIRED` 与 `HIGH_ERROR_RATE` 的矛盾结果。
- 建议同时写入百分比和四位小数，兼顾人工阅读与自动评估。

## 初始失败或薄弱点

- 原严格策略白名单会拒绝 `alert_threshold_error_rate`。
- 原归一化策略没有默认值，也没有有限数值和 0-1 边界校验。
- 原诊断仅按单服务生成，缺少跨服务错误率视角。
- 原 evaluation 没有“阈值下方”和“恰好等于阈值”两个关键边界用例。

## 定向改动

- `src/contracts.ts`：扩展类型化 `Policy` 契约。
- `src/validation.ts`：接受可选字段、应用 0.5 默认值，并拒绝非有限数值及越界值。
- `src/diagnosis-policy.ts`：追加 `HIGH_ERROR_RATE` 聚合诊断，写入实际错误率和全部相关证据 ID。
- `tests/validation.test.js`、`tests/diagnosis-policy.test.js`、`tests/health-agent.test.js`：增加 7 项定向测试。
- `evaluation/` 与 README：补充协议字段、合理性判据和 2 个边界评估用例。

## 调优前后对比

- 改造前定向基线：16/21 通过，5 项与新需求直接相关的测试失败。
- 改造后定向结果：21/21 通过。
- 改造后完整回归：32/32 通过；原 25 项回归测试全部保留并继续通过。
- evaluation：由 10 个用例扩展到 12 个，新增低于阈值和等于阈值的端到端输入。

## 回归检查

- 原诊断码、诊断顺序和服务/总体状态规则保持不变，聚合码只在条件满足时追加。
- 502/503/504 与选定网络错误仍最多重试一次；超时、业务不健康、非法响应等仍不重试。
- 实际 HTTP Abort 超时、整体超时、并发上限、输入顺序和 JSONL 一进一出行为继续通过。
- stdout 仍只有 JSON；评估日志和异常日志仍写入 stderr。
- 最终包使用 manifest 声明的 `node22` 命令，从只读解压目录执行源码测试和 12 行评估输入。

## 剩余风险

- 错误率是单次输入的横截面，不是时间窗口指标，不能替代生产监控中的 SLO、去抖、告警抑制和恢复通知。
- 阈值为 0 时采用“至少一个不健康服务才告警”的业务保护；若评审方将纯数学 `0 >= 0` 解释为无失败也应告警，需重新确认语义。
- 服务数上限为 20，因此引用全部不健康尝试的输出仍受控；若未来放宽上限，需要考虑证据列表大小。
- Mock 仍为单进程、回环地址和确定性场景，不能覆盖真实 DNS、TLS、鉴权和跨网络故障。
