# 第一轮交付与实验结论

日期：2026-09-08。代码版本：0.2.0。结果是工程验证和一个模拟需求的真实接口试跑，尚不是用户价值验证。

## 已交付

- 三条默认实现路线、结构化取舍对比、按条件选择。
- 原文保留、带出处的硬约束、失败评分不再给默认分、硬约束冲突不进入推荐集合。
- 一次提示、普通采样、Stemcell 三组对照，以及可选的“不使用摘要生成”消融组。
- 分阶段调用/token/耗时记录，调用预算、失败用量记录、供应商拒绝时停止批量调用。
- 十个有明确模拟标记的案例、匿名材料、空白人工记录表及报告命令。

Python 3.12 环境中 47 项测试通过；Ruff 检查、格式检查和包构建通过。两个独立检查覆盖了真实模型接口和一个生成步骤的确定性反例。没有修改原始仓库分支或向远程推送。

## 实验范围

离线实验：十个模拟需求 × 三个方法，全部 30 组运行完成，170 次协议模拟调用。离线占位内容不衡量方案质量，token 和费用未知。

正式接口试跑：一个模拟需求“离线笔记导出与恢复”，三个方法各生成三个候选，17 次真实调用，全部返回有效结构。生成与评审都使用提供的 `DeepSeek-V4-Flash` 接口；没有独立模型交叉验证。并发设置为 1，单候选输出上限 1,500；一次提示生成三候选的上限为 4,500。未提供单价，因此不估算金额。

原 `dots3-note-prev` 接口的长请求出现超时和输出未完整结束；另一个接口也遇到一次限流。为验证软件流程，正式试跑使用了另一个已配置接口。这不构成两个模型的公平性能比较。

## 观测数据

下表不含三个方法共同使用的底座提炼：

| 方法 | 生成调用 / token | 评审调用 / token | 总 token | 运行秒数 |
|---|---|---|---|---|
| 一次提示 | 1 / 1,618 | 3 / 3,993 | 5,611 | 182.103 |
| 普通采样 | 3 / 2,364 | 3 / 4,422 | 6,786 | 197.635 |
| Stemcell | 3 / 3,345 | 3 / 4,904 | 8,249 | 210.991 |

共同底座提炼额外使用 1 次调用、557 token、74.647 秒。整个正式试跑为输入 12,825 token、输出 8,378 token，总计 21,203 token。以上不含前面的连接探测和失败排障请求。

这个案例的 Stemcell 生成加评审 token 比一次提示高约 47%。没有人工偏好或执行结果，不能宣称额外开销换来了更好的方案。时延受到本次串行配置、接口响应和模型行为影响，不能推广为方法的一般性能差异。

## 一个必须保留的反例

普通采样的 `clone_01` 提出在当前笔记目录中用 `git checkout -b restore-<tag> <tag>` 恢复历史版本，并声称新建分支不会影响原笔记。裁判把“不得修改或删除原始笔记”判为通过。

在独立临时仓库中建立两个内容不同的版本，再执行相同类型操作，工作文件由当前版本切换为旧版本。因此该步骤并不满足原文的只读要求。检查没有触碰任何用户笔记或用户仓库。

重现：`python docs/experiments/reproduce_git_restore.py`。结构化案例：`examples/judge_counterexample.json`。

这证明：找到一段“不会修改文件”的文字，不等于验证了后续操作的副作用。当前系统仍有评审漏检；界面使用“模型未发现冲突（未实测）”，而不是把这一状态表述成实际验证通过。这个反例不是估计漏检率的足够样本，也不是用户偏好评分。

## 现在应该怎么使用

可用它整理和比较方案，但关键步骤仍要检查。下一轮优先积累带确定性结果的约束反例，检验裁判能否识别“摘要承诺与实施步骤矛盾”。不要用更多角色或更漂亮的总分掩盖这个问题。

用户尚未提供真实需求集。本轮没有把其他项目的内容擅自变成案例，也没有代填人工偏好。需要用有出处的真实需求替换模拟案例，再盲评取舍、修改量和最终采纳情况；总阅读时间也需另做随机分配实验才能评估节省量。
