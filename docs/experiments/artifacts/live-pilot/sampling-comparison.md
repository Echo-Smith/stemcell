## 按条件选择

- 如果个人笔记量不大，附件规模可控，且主要需求是定期备份或迁移；能接受命令行操作，且不要求增量或压缩功能；优先数据安全，可接受手动处理冲突，可考虑路线 1。
- 如果笔记目录适合用 Git 管理（无大文件或可接受仓库体积）；需要简单可靠的版本回滚，且不要求细粒度恢复；希望减少自定义代码，依赖现有工具，可考虑路线 2。
- 如果笔记和附件都在本机，且目录结构稳定；需要定期手动备份，不要求自动化；可接受命令行操作，可考虑路线 3。

### 路线 1：基于目录快照的只读批量导出与恢复

将笔记库视为只读源，通过生成清单文件和复制操作实现批量导出与恢复，全程离线，不修改原始笔记。

**交付范围**

- 批量导出：将指定笔记目录下的 Markdown 文件及其附件目录复制到目标导出目录
- 恢复：从导出目录将内容复制回原笔记库（需用户确认目标路径）
- 生成导出清单（manifest）记录文件相对路径和校验值

**明确舍弃**

- 不支持增量导出或增量恢复
- 不支持压缩打包（如 zip）
- 不支持删除或移动原始文件
- 不支持版本历史或冲突解决

**执行步骤**

- 编写脚本（如 Python 或 shell）遍历笔记根目录，收集所有 .md 文件和附件目录（如 assets/）的相对路径，生成清单文件
- 导出时，按清单将文件复制到目标导出目录，保持相对结构，并写入清单文件（含相对路径和 SHA-256 校验值）
- 恢复时，读取导出清单，将文件复制回用户指定的目标目录（默认原笔记库），若目标文件已存在则跳过或提示，不覆盖任何原始文件

**风险**

- 附件目录结构不统一或存在嵌套，导致清单遗漏
- 恢复时若目标目录已有同名文件，可能造成混淆或误覆盖（需强制只读保护）
- 大规模附件时复制耗时较长，但离线运行无网络风险

**代价**

- 为保原始数据安全，牺牲了恢复时的覆盖能力，需手动处理冲突
- 为减少维护，采用简单脚本而非图形界面，但功能有限
- 为离线运行，放弃云同步和远程备份

**适用条件**

- 个人笔记量不大，附件规模可控，且主要需求是定期备份或迁移
- 能接受命令行操作，且不要求增量或压缩功能
- 优先数据安全，可接受手动处理冲突

**工作量估计：** 约 0.5–1 天开发，不含测试和优化

估计依据：假设开发者熟悉脚本语言，附件规模未知但按普通个人笔记量（<10GB）估计，复制操作简单

**核对：** 模型未发现冲突（未实测）。候选方案完整覆盖所有硬约束，且明确排除增量、压缩、删除原始文件等功能，符合个人工具定位。风险点在于附件目录结构不统一可能导致清单遗漏，以及恢复时同名文件冲突需手动处理，但方案已提供只读保护和跳过提示机制。

- C1 / pass：候选正文明确说明全程离线，且未提及任何网络依赖，符合硬约束C1。；候选证据：全程离线，不修改原始笔记。
- C2 / pass：候选正文明确将笔记库视为只读源，且导出和恢复均采用复制操作，不修改或删除原始笔记，符合硬约束C2。；候选证据：将笔记库视为只读源，通过生成清单文件和复制操作实现批量导出与恢复，全程离线，不修改原始笔记。
- C3 / pass：候选正文明确支持Markdown文件和附件目录，未提及对其他格式的支持，符合硬约束C3。；候选证据：收集所有 .md 文件和附件目录（如 assets/）的相对路径

### 路线 2：基于 Git 仓库的版本化导出/恢复方案

将笔记目录初始化为 Git 仓库，通过提交和标签实现批量导出快照，通过分支或标签检出实现恢复，全程离线运行，不修改原始笔记。

**交付范围**

- 将笔记根目录（含 Markdown 和附件目录）纳入 Git 版本控制
- 提供导出命令：创建提交并打标签（如 export-YYYYMMDD）
- 提供恢复命令：基于指定标签创建新分支并检出，不影响当前工作区
- 编写简单脚本封装上述操作

**明确舍弃**

- 不支持选择性导出/恢复（仅全量）
- 不支持增量恢复或差异合并
- 不支持加密或压缩归档
- 不支持图形界面

**执行步骤**

- 1. 在笔记根目录执行 `git init`，并添加 `.gitignore`（忽略临时文件）
- 2. 创建脚本 `export.sh`：执行 `git add -A && git commit -m "export $(date)" && git tag export-$(date +%Y%m%d)`
- 3. 创建脚本 `restore.sh`：接受标签参数，执行 `git checkout -b restore-<tag> <tag>`（在新分支上恢复）
- 4. 验证恢复结果：检查新分支中的文件与原始文件一致（用 `git diff` 对比）
- 5. 记录操作说明到 README

**风险**

- 附件体积过大导致 Git 仓库膨胀，性能下降（实际规模未知）
- 误操作 `git checkout` 可能覆盖当前工作区（需严格使用新分支）
- Git 不擅长处理二进制附件的大量版本，可能增加存储开销

**代价**

- 利用 Git 成熟机制，维护成本低
- 牺牲选择性恢复能力，恢复为全量快照
- 附件变更历史会永久保留，增加仓库体积

**适用条件**

- 笔记目录适合用 Git 管理（无大文件或可接受仓库体积）
- 需要简单可靠的版本回滚，且不要求细粒度恢复
- 希望减少自定义代码，依赖现有工具

**工作量估计：** 半天到一天

估计依据：假设开发者熟悉 Git 基本命令，且笔记目录无冲突的版本控制

**核对：** 模型未发现冲突（未实测）。方案基于 Git 实现，满足离线、不修改原始笔记、支持 Markdown 和附件目录的硬约束。但存在风险：Git 仓库可能因附件体积过大而膨胀，且恢复操作依赖用户正确使用新分支，误操作可能覆盖工作区。软分数方面，可执行性较高（步骤清晰），取舍明确（全量快照），但风险控制一般（未提供附件规模应对措施）。

- C1 / pass：候选方案明确说明“全程离线运行”，且所有操作均为本地 Git 命令，无网络依赖。；候选证据：全程离线运行
- C2 / pass：候选方案通过创建新分支恢复，且明确“不影响当前工作区”，未提及修改或删除原始笔记。但需注意 `git add -A` 会暂存所有变更，可能修改索引，但不会修改或删除原始笔记内容。；候选证据：不修改原始笔记
- C3 / pass：候选方案明确将笔记根目录（含 Markdown 和附件目录）纳入版本控制，符合第一版只支持 Markdown 和附件目录的约束。；候选证据：将笔记根目录（含 Markdown 和附件目录）纳入 Git 版本控制

### 路线 3：离线批量导出与恢复（只读打包 + 独立恢复）

用只读方式扫描 Markdown 笔记和附件目录，生成 zip 包；恢复时把 zip 解压到新目录，不触碰原始笔记。

**交付范围**

- 导出：将笔记目录（含 .md 文件和附件子目录）打包为 zip，保留相对路径
- 恢复：从 zip 解压到用户指定目录，若目标已存在则自动创建带时间戳的新目录
- 提供命令行入口，支持 --export 和 --restore 参数

**明确舍弃**

- 不做增量/差异导出
- 不支持加密或压缩选项
- 不提供图形界面

**执行步骤**

- 导出：遍历笔记根目录，收集 .md 文件和附件目录（如 images/ 等），用 Node.js 内置 zlib 生成 zip，写入导出文件
- 恢复：读取 zip 条目，逐一解压到目标目录（使用绝对路径，禁止路径穿越检查），不覆盖任何已存在文件
- 校验：导出后输出文件数量、总大小；恢复后输出解压文件数，与 zip 条目数比对

**风险**

- 附件规模过大导致导出时间长或内存不足（需流式写入）
- zip 路径穿越风险（恢复时需校验相对路径）
- 原始笔记中可能有符号链接导致循环或越界

**代价**

- 为满足离线与只读，牺牲了实时同步和选择性导出
- 为减少维护，采用标准 zip 格式，但需处理大文件流式读写

**适用条件**

- 笔记和附件都在本机，且目录结构稳定
- 需要定期手动备份，不要求自动化
- 可接受命令行操作

**工作量估计：** 2-3 天

估计依据：假设：开发者熟悉 Node.js，笔记目录结构简单，附件规模未知但预计不超过数 GB

**核对：** 模型未发现冲突（未实测）。候选方案在硬约束上全部通过，但存在一些待验证事实：附件规模未知，方案假设不超过数 GB，但未提供具体应对措施；恢复时路径穿越检查描述为'禁止路径穿越检查'，表述可能不准确，需确认是否实际执行校验；符号链接处理仅列为风险，未给出具体规避方案。

- C1 / pass：候选方案明确采用本地只读扫描和本地解压，未依赖网络或外部服务，满足离线运行要求。；候选证据：用只读方式扫描 Markdown 笔记和附件目录，生成 zip 包；恢复时把 zip 解压到新目录，不触碰原始笔记。

- C3 / pass：候选方案明确导出范围仅包含 .md 文件和附件子目录，符合第一版只支持 Markdown 和附件目录的约束。；候选证据：导出：将笔记目录（含 .md 文件和附件子目录）打包为 zip，保留相对路径
