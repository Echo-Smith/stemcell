### 路线 1：纯脚本导出+恢复（Bash/Python）

用 Python 标准库编写一次性脚本，扫描笔记目录，将 Markdown 和附件复制到导出文件夹，并生成恢复用的反向映射脚本。

**交付范围**

- 导出：复制 .md 文件和附件目录到指定导出路径
- 恢复：从导出目录复制回原目录，仅覆盖目标文件
- 生成恢复脚本（.sh 或 .py）供手动运行

**明确舍弃**

- 不提供 GUI 或交互式界面
- 不支持增量导出或压缩打包
- 不处理文件名冲突（直接覆盖）

**执行步骤**

- 1. 编写 Python 脚本，遍历笔记根目录，收集 .md 文件和附件目录（如 assets/）
- 2. 复制文件到导出目录，保持相对路径
- 3. 生成恢复脚本，记录源路径和目标路径，恢复时逐文件复制

**风险**

- 附件规模大时复制慢或磁盘不足（未知）
- 恢复脚本可能因路径变化而失效（如移动导出目录）

**代价**

- 零依赖，维护简单
- 恢复是手动触发的，不是自动集成

**适用条件**

- 希望快速实现且不介意命令行操作
- 附件规模小到中等，且目录结构简单

**工作量估计：** 1-2 天

估计依据：假设熟悉 Python 文件操作，附件规模未知但脚本线性处理

**核对：** 模型未发现冲突（未实测）。候选方案为纯脚本实现，满足所有硬约束。但存在风险：未处理文件名冲突（直接覆盖）可能违反 C2 的“不得修改或删除原始笔记”精神，因为覆盖目标文件可能覆盖原始笔记（若导出目录与源目录重叠或路径映射错误）。此外，恢复脚本可能因路径变化失效，需在实施中验证。软分数：可执行性高（标准库、步骤清晰），取舍清晰（明确排除 GUI、增量等），风险控制中等（未充分处理冲突和路径变化）。

- C1 / pass：使用 Python 标准库，无外部依赖，可离线运行，符合硬约束。；候选证据：用 Python 标准库编写一次性脚本
- C2 / pass：恢复操作仅覆盖目标文件，未提及修改或删除原始笔记，且导出为复制操作，符合硬约束。；候选证据：恢复：从导出目录复制回原目录，仅覆盖目标文件
- C3 / pass：明确只处理 .md 文件和附件目录，符合第一版只支持 Markdown 和附件目录的硬约束。；候选证据：导出：复制 .md 文件和附件目录到指定导出路径

### 路线 2：Git 仓库版本控制+导出归档

将笔记目录初始化为 Git 仓库，利用 git archive 导出快照，恢复时用 git checkout 或直接解包。

**交付范围**

- 初始化 Git 仓库（若尚未初始化）
- 导出：git archive 生成 tar/zip 快照
- 恢复：从快照解压回原目录，仅覆盖现有文件

**明确舍弃**

- 不提供选择性导出（整库导出）
- 不处理二进制附件的大文件优化（Git 会全量存储）
- 不自动提交，需手动 commit

**执行步骤**

- 1. 在笔记根目录运行 git init（若未存在）
- 2. 提交当前状态作为基线
- 3. 导出时 git archive -o backup.zip HEAD
- 4. 恢复时解压 zip 到原目录（覆盖文件）

**风险**

- 附件规模大时 Git 仓库体积膨胀，导出慢
- 误操作 git 可能影响原始文件（但硬约束要求不修改原始笔记，需谨慎）

**代价**

- 自带版本历史，便于追踪变化
- 维护成本低（Git 工具成熟）
- 但恢复是手动解压，且要求用户理解 Git

**适用条件**

- 笔记已有 Git 习惯或愿意采用
- 附件以文本为主，或能接受 Git 存储大文件

**工作量估计：** 半天到 1 天

估计依据：假设熟悉 Git 基本命令，附件规模未知但 Git 存储效率取决于类型

**核对：** 模型发现硬约束冲突。方案采用 Git 实现离线导出，但恢复时覆盖原文件直接违反硬约束 C2，需调整恢复策略（如恢复到新目录）。此外，方案未明确附件规模处理，存在风险。

- C1 / pass：方案完全依赖本地 Git 操作，无网络依赖，满足离线运行要求。；候选证据：初始化 Git 仓库（若尚未初始化）
- C2 / fail：恢复步骤明确要求覆盖原目录文件，可能修改原始笔记，违反不得修改或删除原始笔记的硬约束。；候选证据：恢复时解压 zip 到原目录（覆盖文件）
- C3 / pass：方案仅针对 Markdown 和附件目录进行导出，未涉及其他格式，满足第一版只支持 Markdown 和附件目录的要求。；候选证据：导出：git archive 生成 tar/zip 快照

### 路线 3：增量备份工具（rsync 或 restic）

使用 rsync（Linux/macOS）或 restic（跨平台）进行增量备份，导出和恢复均通过命令行完成，支持加密和去重。

**交付范围**

- 导出：rsync 或 restic backup 到外部存储
- 恢复：rsync 或 restic restore 到原目录
- 支持增量备份（只传变更文件）

**明确舍弃**

- 不提供 GUI，依赖命令行
- restic 需要初始化仓库（首次配置）
- rsync 不提供加密（restic 有）

**执行步骤**

- 1. 安装并配置工具（rsync 通常预装，restic 需下载）
- 2. 定义备份目标路径（如外接硬盘）
- 3. 运行备份命令（rsync -a 或 restic backup）
- 4. 恢复时运行对应 restore 命令

**风险**

- rsync 误操作可能覆盖原始文件（需小心参数）
- restic 仓库损坏可能导致恢复失败（需定期检查）

**代价**

- 增量备份高效，适合大附件
- 维护成本低（工具成熟）
- 但需要学习工具特有命令和概念

**适用条件**

- 附件规模可能很大，且希望备份效率高
- 愿意接受命令行工具并投入少量学习时间

**工作量估计：** 1-2 天（含配置）

估计依据：假设熟悉命令行，附件规模未知但增量备份可应对大附件

**核对：** 有约束待核实。候选方案基于 rsync/restic 实现增量备份，满足离线、不修改原始笔记（需谨慎参数）和仅支持 Markdown/附件目录的硬约束。但方案未提供具体防止误操作的保护措施，且未明确附件规模对备份策略的影响，风险控制有待加强。

- C1 / pass：候选方案明确使用本地命令行工具，未依赖网络服务，满足离线运行要求。；候选证据：使用 rsync（Linux/macOS）或 restic（跨平台）进行增量备份，导出和恢复均通过命令行完成
- C2 / pass：候选方案在风险中明确提示 rsync 可能覆盖原始文件，并强调需小心参数，表明方案设计上避免修改或删除原始笔记，但未提供具体保护措施，因此判定为 pass 但风险较高。；候选证据：rsync 误操作可能覆盖原始文件（需小心参数）
