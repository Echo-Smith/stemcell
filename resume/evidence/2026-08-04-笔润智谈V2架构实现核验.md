## 一、双模式 Agent 与退出边界

### 已实现证据

- `backend/internal/config/config.go` 定义 `AGENT_MODE=pipeline|unified`，服务端也允许请求参数覆盖运行模式。
- `backend/internal/engine/engine.go` 实现固定 `[]Step` Pipeline。
- `backend/internal/agent/unified_agent.go` 实现 ReAct 循环，由 LLM 选择工具，同时用规则强制补齐关键步骤，默认最多 12 轮。
- `backend/internal/server/server.go` 将 Steps、内置工具和 MCP 工具统一注册到 `ToolRegistry`，按模式选择 `AgentEngine` 或 `UnifiedAgent`。

### 五个共用退出 / 暂停机制

1. 用户取消；
2. 全局上下文超时；
3. Token 预算耗尽；
4. 客户端断连后暂停；
5. 连续 LLM 失败达到阈值后触发断路器。

额外边界：

- UnifiedAgent 默认最多执行 12 轮；
- 人工提纲确认支持独立超时；
- AutoFix 支持最大修复次数；
- 配额耗尽单独硬停止。

### 测试状态

- `backend/internal/engine/exit_test.go` 覆盖预算、取消、上下文超时、断连、断路器、确认超时、单步超时、关键 / 非关键步骤降级等行为。
- `backend/internal/agent` 当前没有独立测试文件，因此不宜声称“UnifiedAgent 的所有退出场景均完成自动化回归”。

### 推荐简历表达

> 保留固定 Pipeline 保障关键步骤顺序，以 ReAct UnifiedAgent 按状态选择工具；统一设置取消、全局超时、Token 预算、断连暂停和连续 LLM 失败断路器，并以迭代上限和人工确认超时避免无限等待。

## 三、编辑部三 Agent 编排

### 已实现证据

- `Orchestrator` 管理研究 Agent、写作 Agent、审校 Agent，并以 Task、Artifact、Event、Decision、Transition 表达状态和协作协议。
- 研究、写作、审校分别有执行器，产出研究简报、初稿 / 修改稿、审校报告等版本化交付物。
- `editorial_agent_leases` 与部分唯一索引保证同一任务、同一角色只能存在一个活跃 Lease；完成后释放，可再次获取。
- 研究质量按信源数、信息缺口和已核验事实路由：高质量自动进入写作，中质量进入人工 Decision，低质量最多自动重试 2 次后升级人工。
- 写作质量按字数和结构路由：质量充分自动进入审校，偏短进入人工确认，空稿重试后升级。
- 审校通过进入待发布；一般问题退回写作；严重问题进入人工裁决。
- Decision 保存批准 / 驳回后的目标状态，并支持 Decision Packet 汇总决策上下文。

### 测试状态

- 纯逻辑单元测试覆盖状态机、Decision 映射、Actor、交付物角色、Decision Packet 指标提取、知识生命周期等。
- Lease、动态质量路由、Decision 解析与三 Agent E2E 测试文件均已存在。
- 本次环境未配置 `TEST_DATABASE_URL`，上述 PostgreSQL 集成 / E2E 用例被测试框架跳过，不能写成“数据库端到端回归已通过”。

### 推荐简历表达

> 将研究、写作、审校三类 Agent 编排为版本化协作流，以数据库 Lease 防止重复执行，按研究信源、信息缺口、稿件结构和审校严重度动态路由；低质量任务有限重试后进入人工 Decision，支持批准、退回与接管。

## 四、MCP 双向能力

### 已实现证据

- 客户端支持初始化、`tools/list`、`tools/call`，可把外部 MCP 工具注册为 `mcp__<server>__<tool>` 并交给 UnifiedAgent 使用。
- 进程内 MCP Server 支持 `initialize`、`tools/list`、`tools/call`，可暴露搜索、风格、记忆、LLM 和知识库等内置能力。
- 服务端协议、工具列表、工具调用、stdio Reader 和 HTTP Handler 有单元测试。

### 不能使用“完整 MCP 双向支持”的原因

- 客户端标注的 `sse` 传输实际执行 HTTP POST 并读取一次性 JSON 响应，没有建立标准的长连接事件流。
- 服务端 HTTP 处理器同样返回普通 JSON；更准确的叫法是“HTTP JSON-RPC 传输”。
- `startMCPServerStdio` 已实现但未发现主启动流程调用。
- MCP 客户端测试主要覆盖类型解析与工具命名，未覆盖真实外部进程的 initialize → list → call 端到端链路。
- UnifiedAgent 将 MCP 输出加入对话，但当前未发现 MCP 输出路径显式调用 Prompt Injection 清洗。

### 推荐简历表达

> 实现 MCP 客户端接入与进程内 MCP Server 原型：将外部工具注册进 Agent ToolRegistry，并把搜索、记忆、知识库等内置能力以 JSON-RPC 工具方式对外暴露。

面试前不建议说：

> 完整支持所有 MCP 传输协议 / 已通过多个外部 MCP Server 生产验证。

## 五、可观测性、Trace 与日志

### 指标

- `MetricsRegistry` 注册并通过 `/metrics` 暴露 19 个 Prometheus 文本格式指标族。
- 当前实际接入业务埋点的有 6 个：HTTP 请求量、HTTP 时延、WebSocket 活跃连接、WebSocket 错误、Agent 执行量、Agent 时延。
- LLM、Profile Cache、Evaluation、Database、Grayscale 等 13 个指标族目前只完成注册，未发现业务代码中的 `Inc / Observe / Set` 接线。
- 自定义 exporter 使用 `v0 / v1` 作为标签名，尚未输出定义时声明的 `method / path / status` 等语义标签名。

因此简历不使用“15+ 生产指标全链路监控”，可改为：

> 搭建 Prometheus 兼容指标出口，已接入 HTTP、WebSocket 与 Agent 的 6 个核心指标族，并预留 LLM、评测、数据库和灰度指标。

### DB Trace

- `agent_traces` 保存输入、模式、状态、步骤历史、文章、审校结果、Token、耗时、错误和推理内容。
- 请求开始创建 Trace，结束时完成或标记失败，并可关联编辑部任务与交付物。
- `UpdateTraceStep` 已实现但未发现调用；当前数据库主要在任务结束时写入最终步骤历史，不宜描述为“每一步实时持久化”。

推荐表达：

> 将 Agent 最终步骤历史、Token、耗时、审校结果和错误写入 PostgreSQL Trace，并关联编辑部任务，支持历史查询与问题追溯。

### 结构化日志

- 入口通过 `slog.NewJSONHandler` 初始化全局 JSON 日志。
- 主要链路记录 `trace_id`、step、iteration、duration、token、error 等结构化字段。
- `LOG_FORMAT` 虽存在配置项，但 logger 当前始终输出 JSON。
