## 一、这轮电话的真实目标

这次大概率仍是 HRO / 供应商侧的前置沟通，不一定立即进入完整业务面。对方主要确认四件事：

1. 简历中的 Prompt、Memory、Eval、Badcase 是否来自真实实践；
2. 正式工作是内容运营，为什么能够转向 Agent 效果策略；
3. 能否接受外包，以及薪资、地点、到岗时间等基本条件；
4. 是否值得把候选人继续推荐给小红书业务团队。

电话沟通的目标不是证明自己已经做过小红书同等规模的生产系统，而是让对方确认：

> 有真实用户和输出反馈，能稳定判断 Agent 输出好坏，能把问题归因到 Prompt、Context、Memory、工具、流程或运行层，并具备把策略做成可复核评测与修复闭环的能力。

## 二、必须守住的三条事实边界

### 1. 正式 AI 产品年限

- 正式岗位是内容运营，不是 AI 产品经理；
- 笔润智谈从 2026 年 3 月开始，不能回答成“一年以上正式 AI 产品经验”；
- 可以强调的是：有真实作者使用、端到端产品实践和可现场展示的代码与产品。

推荐口径：

> 我没有一年以上正式 AI 产品岗位 title，这一点我会如实说明。我的优势是从 2026 年 3 月开始独立做笔润智谈，V1 已经有真实作者完成写作任务，V2 进一步把 Prompt、Memory、Agent 编排、评测和 Trace 做成完整产品机制，所以我缺的是正式岗位年限，不是只停留在概念层的实践。

### 2. V1 与 V2 的成熟度

- V1：已部署并有真实内容生产使用；覆盖 200+ 名体验用户，其中 53 名作者完成真实写作任务；
- V2：已有 14 名内测用户、近 70 条完整任务样本，代码实现与本地构建已核验；部署和生产稳定性尚未验证；
- V2 的 Trace、评测、自动触发和版本比较是本地系统能力，不能说成“小红书规模的线上闭环”。

推荐口径：

> V1 的 Badcase 来自真实作者使用；V2 是我针对这些问题重新设计的版本，目前已经完成主要功能和本地验证，但还没有完成正式部署。因此我会区分真实线上反馈、本地回归结果和未来生产验证，不把三者混在一起。

### 3. 评测体系成熟度

- 已实现：按风格拆分评测集、样本与维度结构、规则评分、单模型 LLM-as-Judge、评测运行记录、Profile 发布触发、版本结果对比；
- 已存在三类种子评测集：深度时评 25 条、申论 20 条、小红书内容 20 条，共 65 条；这些是离线种子样本，不是 65 名真实用户；
- 尚未完成：生产级人类金标校准、多人标注一致性、在线 A/B、Judge 多次采样或多模型仲裁；
- “近 70 条完整任务样本”是 V2 用户任务口径，不等于离线评测集。

推荐口径：

> 我已经搭出了可运行的离线评测结构，但不会把它称为成熟 Benchmark。当前是规则校验加单模型 Judge 的第一阶段，下一步必须用人工金标校准一致性，再接入线上 Badcase 和版本发布门禁。

## 三、90 秒自我介绍

> 您好，我目前有接近两年的内容平台、质量审核和跨团队项目推进经验。我的正式岗位虽然是内容运营，但长期面对的核心问题是内容质量怎么定义、不同平台和用户的偏好如何区分，以及发现问题后怎样形成稳定规则。
>
> 今年 3 月我独立发起了 AI 写作产品笔润智谈。V1 覆盖了 200 多名体验用户，其中 53 名作者完成过真实写作任务。我根据真实反馈处理过三类典型问题：输出逻辑更清晰但格式趋同，我调整了 Prompt 规范；标题和个人视角存在差异，我没有继续堆全局 Prompt，而是引入按用户和适用范围生效的 Memory；批量查重失败则被归因到并发和运行稳定性，而不是模型内容能力，随后重构了兜底链路。
>
> V2 进一步实现了 Pipeline 与 ReAct 双模式、分层记忆、规则加 LLM-as-Judge 的评测以及 Trace 追溯。目前它仍处于内测和本地验证阶段，我不会把它包装成生产级平台。这个岗位吸引我的地方，是它正好把我最擅长的“判断输出—拆解原因—设计策略—评测回归”变成完整职责，我希望进入真实 C 端业务继续把这套能力做深。

建议控制在 80—100 秒。不要在自我介绍中主动展开 MCP、Prometheus、Go 或数据库结构。

## 四、HRO / HR 高频问题与回答

### Q1：为什么想换工作？

> 我目前的工作让我积累了内容质量、平台分发、用户反馈和复杂协作经验，但 AI 产品更多依靠个人项目推进。我已经确认自己真正想长期做的是 AI 产品效果和用户体验，希望下一步进入有真实产品、用户反馈和算法协作的团队，把个人实践升级为正式业务能力。这是职业方向的主动收敛，不是对当前工作的否定。

### Q2：为什么选择 Agent 策略产品运营，而不是普通产品经理？

> 我最强的证据不是画了多少原型，而是能对输出好坏做拆解。我会区分事实错误、结构问题、风格不匹配、记忆污染、工具失败和运行异常，再选择 Prompt、Memory、Agent 路由、规则或人工接管处理。这个岗位要求的正是效果判断和修复闭环，比泛产品岗位更贴合我的真实实践。

### Q3：你没有一年正式 AI 产品经验，为什么认为自己能胜任？

> 年限这项我确实不是完全匹配，我不会把个人项目包装成正式任职。我的补偿项有三个：第一，产品不是纯 Demo，V1 有真实作者完成任务；第二，我亲自完成了从需求、策略、实现到评测的端到端闭环；第三，我有内容质量判断和真实平台运营经验。是否能胜任最终应该看我能否讲清 Badcase、归因和验证，而不只是看 title。

### Q4：为什么对小红书感兴趣？

> 小红书的内容价值高度依赖真实体验、个体表达和社区语境，Agent 输出不能只做到语法正确，还要避免模板化、虚假确定性和对用户个性的覆盖。这与我在笔润智谈中遇到的格式趋同、标题伦理和个人视角问题很接近。另一方面，小红书官方岗位也在强调任务完成度、相关性、工具调用准确率、安全性以及离线评测和在线实验，说明团队把 Eval 当作产品能力，而不是上线前的一次测试。

### Q5：能接受外包吗？

> 我愿意继续了解，也不会仅因为外包形式直接否定机会。但我会重点确认三件事：是否能接触真实 Badcase 和实验数据，是否实际参与策略设计而不只是标注执行，以及合同、薪酬和绩效主体是否清楚。如果工作内容确实能形成 Agent 效果闭环，我会认真评估。

不要回答“为了进小红书，外包也无所谓”。这会削弱议价能力，也暴露职业判断不足。

### Q6：期望薪资是多少？

> 我看到了职位发布的薪资区间，希望结合实际职责、固定薪资与绩效结构，在区间内讨论。现阶段我的优先级是确认工作是否真正涉及策略设计、评测和线上闭环，确定岗位边界后我可以给出更具体的期望。

如果对方必须要数字，可使用：

> 结合岗位要求和我的匹配度，我希望税前月薪在 15K—18K 范围内讨论，具体也会综合年终奖、社保公积金基数和加班情况。

此处仍需结合当前薪资和个人底线最终确认。

### Q7：最快什么时候到岗？

需按真实情况补充，不要猜：

> 我目前在职，正式到岗需要按照现单位交接安排。我可以尽快推进流程，确认 offer 和合同主体后，再给出准确日期。

## 五、笔润智谈项目深挖

### Q8：为什么要做笔润智谈？

> 起点不是“我想做一个 Agent”，而是内容生产中反复出现四类问题：资料核验分散、通用模型输出容易同质化、不同作者偏好冲突、多轮返工缺少版本和责任边界。V1 先把写作、润色和查重三个高频任务做出来验证，得到真实反馈后，V2 才扩展为研究、写作、审校协作流。

追问“用户原来怎么做、53 名作者来自哪里”时，必须按真实情况回答，当前材料尚未确认这部分，见文末待补事实。

### Q9：V1 到 V2 最关键的产品变化是什么？

> V1 更像任务工具，重点是完成一次写作或改写；V2 的产品判断是，内容质量问题往往不是一次生成能解决的，而是研究、写作、审校和用户确认之间的协作问题。所以我没有单纯扩大 Prompt，而是把过程拆成版本化交付物和决策节点，让低质量结果可以重试、退回或交给用户接管。

### Q10：讲一个完整的 Badcase 修复案例。

推荐首讲“格式趋同”：

> 有用户反馈，系统能把逻辑梳理得更清楚，但输出格式越来越像，用户甚至认为需要自己重新换指令。我先把它拆成两个维度：逻辑增强是有效的，表达多样性是失败的。归因后发现问题主要来自全局写作规范对固定句式的强化，所以我没有调整模型或增加 Agent，而是收紧 Prompt 中的模板化句式，并把表达多样性独立纳入质量判断。这个案例让我确认，效果优化不能只看总分，需要保留维度之间的张力。

边界：目前有真实反馈和策略动作，但没有量化的修复前后对照，不能声称“同质化下降多少”。

### Q11：为什么标题伦理问题用 Memory，而不是继续改全局 Prompt？

> 反馈里既有普遍性的质量要求，也有作者个人价值取向。比如使用伤亡数字做标题，有人认为醒目，有人认为标题党；如果直接写进全局 Prompt，会把一个人的偏好错误地施加给所有用户。因此我把长期偏好按用户、来源和适用范围保存，让个人表达边界只在相关用户和任务中生效。这个决策的重点不是记得更多，而是控制记忆的作用范围。

### Q12：你的 Badcase 如何分类？

> 我会先按发生层级分类，而不是一上来改 Prompt：
>
> 1. 输入与意图：用户目标不清或识别错误；
> 2. Context 与知识：材料缺失、过期、检索不相关；
> 3. Prompt 与策略：约束冲突、指令不清或模板化；
> 4. Memory：错误写入、召回不当、偏好过期或作用域污染；
> 5. Planning 与 Tool：步骤遗漏、工具选错、参数错误；
> 6. 模型输出：事实、逻辑、风格和安全问题；
> 7. 系统运行：超时、断连、并发失败和配额问题；
> 8. 交互预期：结果本身可用，但用户不知道 Agent 做了什么、能否修改或如何接管。
>
> 分类后再选择最小修复层，避免所有问题都用加 Prompt 解决。

### Q13：你一般怎么调 Prompt？

> 我的流程是固定 Badcase、复现、归因、做最小改动，再用固定样本回归。首先判断它是不是 Prompt 问题；如果是，就把模糊要求转成可判断的规则，同时避免不同约束互相冲突。改完不会只看一个漂亮输出，而是回放原 Badcase、相邻场景和正常样本，观察是否修复以及有没有副作用。笔润智谈的模板化句式就是按这个过程处理的。

### Q14：四层 Memory 分别解决什么问题？

> 工作记忆保存当前长任务的步骤摘要，防止上下文越做越长；短期记忆保留近期会话，支持多轮衔接；长期记忆保存经过筛选的用户偏好，例如标题风格和表达边界；实体关系网络用于组织人物、栏目、主题及其关系。产品上最重要的是不同记忆有不同生命周期、来源和作用域，而不是把所有历史聊天都塞回 Prompt。

### Q15：如何避免 Memory 污染？

> 我会设置四道门：第一，一次性任务信息默认不进入长期记忆；第二，保留来源、置信度、出现次数和适用范围；第三，新旧偏好冲突时不直接覆盖，要保留替代关系或等待用户确认；第四，用户可以查看、修改和删除记忆。对于敏感信息、低置信推断和高风险偏好，默认不自动沉淀。

其中“来源、置信度、出现次数、状态与替代链”已有代码结构；完整遗忘策略仍在完善，不要回答成已完成生产验证。

### Q16：为什么同时保留 Pipeline 和 ReAct？

> 两者解决的不是同一个问题。写作场景中，资料检索、审校和关键确认不能被随意跳过，因此固定 Pipeline 适合高确定性、高风险步骤；ReAct 更适合需要根据上下文灵活选择工具的任务。我保留双模式，让关键步骤有确定性，复杂任务保留自主性。低质量或高风险结果不会无限自主循环，而是有限重试后转人工批准、退回或接管。

### Q17：Agent 常见失败模式有哪些？你做了什么？

> 我关注五类：目标漂移、循环不退出、工具调用失败、上下文或记忆污染、结果不可解释。系统层设置了用户取消、全局超时、Token 预算、断连暂停和连续模型失败断路器，另外还有迭代上限和人工确认超时。产品层则保留步骤展示、Trace、批准、退回和接管。我的理解是，Agent 体验不只取决于最终答案，也取决于用户是否能预测和控制过程。

## 六、Eval、Rubric 与 LLM-as-Judge 深挖

### Q18：你如何定义 Agent 输出“好”？

> 我会先看任务是否完成，再看完成方式是否可信。对内容 Agent，我拆成事实完整性、相关性、结构、风格、个性化、风险和任务完成度；对带工具的 Agent，还要看规划是否合理、工具是否选对、参数是否正确，以及失败时能否降级。C 端还需要加入用户理解成本、等待时间、人工修改量和是否愿意继续使用。不能只用一个总分掩盖安全或事实错误。

### Q19：评测集怎么分层？

> 我会先按真实用户任务分，而不是按技术模块分。基础维度包括任务类型、难度、风险等级、是否需要工具、是否依赖记忆和失败类型；样本来源分为真实任务 Trace、用户反馈 Badcase、边界场景和合成对抗样本。固定回归集与日常新增样本要分开，避免每次都针对同一批题过拟合。
>
> 在笔润智谈 V2 中，我目前按写作风格维护三类离线种子集，共 65 条；同时保留 V2 的近 70 条用户任务作为另一类真实任务证据。两种样本不能混为一谈。生产环境还需要按用户量和风险分布重新采样。

### Q20：Rubric 怎么设计，才能减少拍脑袋？

> 第一，把任务完成和安全类指标设成硬门槛，不能被文风分数抵消；第二，每个维度写清定义、1—5 分锚点和正反例；第三，能用规则判断的长度、关键词、格式、工具调用结果不交给 LLM；第四，风格、逻辑和表达等语义维度再交给 Judge；第五，用人工金标检查 Judge 与人的一致性，并定期复核分歧样本。

当前项目已经实现规则加 LLM Judge，但完整分数锚点、人类金标校准仍需补齐。

### Q21：为什么要把规则评分和 LLM-as-Judge 结合？

> 因为不同指标的可验证性不同。字数、关键词覆盖、是否命中禁止模式等有确定答案，用规则更稳定、更便宜；事实、逻辑和风格需要语义判断，适合用 LLM Judge。把两者结合，可以减少 Judge 在简单问题上的随机性，也避免规则系统无法理解语义。

### Q22：LLM-as-Judge 有哪些偏差？如何处理？

> 常见问题包括偏好更长、更完整的答案，偏好与自身生成风格相似的答案，对 Prompt 和评分顺序敏感，以及不同轮次尺度漂移。如果是成对比较，还要防位置偏差。
>
> 我的处理思路是：把确定性维度交给规则；建立人工金标集做一致性校准；对高风险或分歧样本进行多人复核；比较模型时隐藏模型身份并交换答案顺序；必要时多次采样或多 Judge 仲裁；持续追踪 Judge 与人工结论的偏差，而不是把 Judge 分数当成绝对真相。
>
> 我当前项目只完成了规则加单 Judge 的初步实现，所以会明确说这些是下一阶段生产化需要补齐的能力。

### Q23：你的自动化评测 Loop 到什么程度？

> 已实现评测集、样本、运行记录、规则加 LLM Judge、Profile 发布触发、结果聚合和版本比较。本地也有 9 条任务的基准报告，用于观察耗时、步骤和审校结果。但 V2 尚未部署，自动评测还没有成为真实线上发布门禁，也没有在线 A/B 和人工一致性校准。因此准确表述是“自动化评测链路已实现并完成本地验证”，不是“生产级 Eval 平台已经运行”。

不要主动引用报告中的“人工节省 99.3%”或“136.9 倍”，其人工基线属于估算，不是可靠用户结果。

### Q24：线上 Badcase 如何形成闭环？

> 我会建立“回收—聚类—归因—修复—回归—灰度—复盘”链路。回收时关联用户任务、模型版本、Prompt 版本、工具调用和 Trace；聚类后区分高频问题与高风险问题；修复时选择最小策略层；离线回归通过后再灰度，关注主指标与安全、时延、成本等护栏；确认有效后，把案例、归因和修复方式沉淀为策略资产。

当前个人项目已经具备反馈、Trace、评测和版本结构，但灰度流量与线上 A/B 尚未完成。

### Q25：如果让你设计 C 端 Agent 的指标，你怎么做？

> 主指标要回到用户任务，例如有效任务完成率或用户确认完成率。效果指标包括相关性、事实正确、工具调用成功、个性化匹配和人工修改量；行为指标包括完成、重试、中断、回访和重复使用；护栏包括安全违规、错误执行、时延、成本和人工接管率。不同任务要分层，不能把闲聊满意度与高风险工具执行放在同一个总分里。

## 七、HearHer 评测项目深挖

### Q26：为什么要测试 ASR，而不是直接测试推荐结果？

> 因为这是高风险情绪场景，语音入口一旦漏掉否定词或风险词，后面的意图判断可能完全反转。我们先把链路中最不可逆的错误找出来，所以重点测试否定词和风险词的保留，再比较 LLM 的指令遵循和安全表现。它体现的是从风险反推评测，而不是为了做模型榜单。

### Q27：177 条音频和 30 条用例怎么理解？

> 177 条是合成音频测试集，用于比较 4 款 ASR；其中重点观察 48 条否定词和 36 条风险词样本。30 条是产品级用例，用于比较不同 LLM 在状态理解、指令遵循和安全边界上的表现。累计完成 700 多次调用。样本以合成为主，所以结论只用于初步选型，不能外推为真实妈妈群体的生产表现。

### Q28：HearHer 的最大局限是什么？

> 最大局限是真实用户和真实环境音频不足。合成样本适合快速覆盖风险词和边界场景，但无法代表口音、噪声、情绪化表达和真实设备差异。如果继续推进，我会先补真实授权样本、噪声分层和人工复核，再决定 ASR 与 LLM 的生产方案。

## 八、产品 Sense 与履历追问

### Q29：举一个“答案看似正确，但产品体验不好”的例子。

> 笔润智谈中有一次输出逻辑完整、观点也全面，但用户不接受标题和表达视角。模型层面它可能得分不低，产品层面却失败了，因为它覆盖了作者自己的价值取向。另一个例子是 Agent 给出正确结果，但用户不知道使用了哪些资料、为何这样修改，也不知道能否撤回，这会降低信任。C 端 Agent 的“好”必须包含可理解、可预期和可控制。

### Q30：内容运营经验和 Agent 策略有什么关系？

> 我不会把内容运营包装成产品经理经历，但它提供了三个直接相关的能力：第一，长期判断不同平台和用户语境下什么内容合适；第二，处理事实、风格、风险和反馈之间的冲突；第三，把多方意见转成可执行规则并复盘。AI 项目让我进一步把这些经验结构化为 Prompt、Memory、Rubric 和 Badcase 分类。

### Q31：你有跨产品、算法、后端协作经验吗？

> 这项是我的缺口之一。笔润智谈主要由我端到端推进，HearHer 是两人团队；正式工作中有多方内容协作和内部 SaaS 验收，我提交过 6 项分级问题、复现路径和关键字段，协助开发定位问题。我具备跨角色沟通和把问题说清楚的能力，但还没有在大规模算法团队中担任正式 Owner。我希望下一份工作补足的正是这部分。

### Q32：AI Coding 生成了多少代码？你本人做了什么？

> 我不会用 AI 生成代码比例证明能力。我的责任是定义用户问题、版本边界、状态和数据结构，判断架构取舍，拆分任务，并对生成结果做代码审查、测试和事实核验。例如 Pipeline 与 ReAct 为什么并存、Memory 为什么要按来源和作用域管理、哪些步骤必须人工确认，这些都是我先做的产品和系统决策。AI Coding 提升交付速度，但需求、判断和验收由我负责。

### Q33：为什么 V2 还没部署？

> V2 的范围从单次写作工具扩展到记忆、编辑部协作、评测和可观测性，我没有为了简历抢跑上线。目前主要功能、本地测试和构建已经完成，但数据库依赖的部分 E2E、正式部署、监控阈值和真实流量验证还需要补齐。我更愿意准确说它处于内测和生产化准备阶段，而不是把可运行代码说成稳定线上产品。

## 九、正式工作经历深挖

### 1. 一分钟工作介绍

> 我目前的正式岗位是内容运营，主要围绕城市品牌传播做内容供给、平台分发和质量协同。我的工作不是单纯写稿或上传，而是承接传播目标，把它拆成选题、素材组织、约稿、审核优化、平台适配、发布监测、反馈回收和归档几个环节。
>
> 日常覆盖微博、今日头条、小红书及矩阵账号。我会根据平台内容形态和传播节点调整标题、表达方式、更新节奏，并参与稿件、话题和评论反馈的分级处理。协作方面，我需要衔接内容提供方、内部业务团队、平台账号和创作者资源，推动内容按要求完成审核与刊发。数据上主要看供给完成度、发布时效、平台反馈和阶段传播表现，并通过看板和复盘发现分发或内容质量问题。
>
> 这段经历让我形成了一套比较稳定的工作方式：先定义什么内容适合当前用户和平台，再把问题分类、制定规则、跟踪结果并迭代。这也是我后来做 Agent Badcase、Rubric 和效果策略时可以迁移的能力。

控制在 55—70 秒。对方没有追问时，不主动展开具体业务主体和敏感响应机制。

### W1：你日常具体负责什么？

> 我可以把日常工作分为四块。第一是内容供给，围绕阶段主题进行选题、素材组织、约稿和审核优化；第二是分发，根据微博、今日头条、小红书的内容形态做标题、篇幅和发布时间适配；第三是质量与反馈，监测发布结果，参与稿件、话题和评论反馈的分级处理；第四是流程协同，推动内容提供方、账号运营方和内部业务团队完成审核、发布、反馈和归档。

不要回答成“每天发稿、做表、上传系统”。这些是执行动作，不是工作的完整目标与结构。

### W2：这些内容是你本人创作的吗？

> 内容来源比较多，包括合作方投稿、业务团队提供、约稿和部分自制内容。我不是所有稿件的作者，主要承担中间层的选题建议、内容审核优化、平台适配、流程推进和发布复盘。2025 年有 99 件稿件通过这套协同流程获得相关专栏刊发，这是团队供给结果，不是我个人写了 99 篇。

这是必须主动说清的归属边界。可以补充本人做过视频、话题文案和 AIGC 漫画，但不要用这些个别产出覆盖主要职责。

### W3：你怎么判断一条内容质量好不好？

> 我通常分四层判断。第一是事实与信息是否准确完整；第二是表达是否适合目标平台和受众；第三是标题、结构和素材是否能让用户快速理解重点；第四是是否存在平台规则、传播风险或敏感信息问题。发布后再结合用户反馈、传播表现和异常情况，判断问题来自选题、表达、分发时机还是渠道适配。

与 Agent 岗位的连接点：这与 Rubric 设计很像，不能只用“感觉不错”评价内容，而要把质量拆成可解释维度。

### W4：微博、今日头条和小红书的分发策略有什么区别？

> 微博更依赖话题节点、实时性和短信息密度，标题和首屏需要尽快建立事件关联；今日头条更适合信息完整、结构清楚的图文，标题要准确说明内容价值；小红书更强调具体场景、用户视角和视觉表达，生硬的通稿感通常不合适。我不会简单复制同一份内容，而是保留核心事实，再调整标题、叙事入口、篇幅、素材组合和发布节奏。

如果被追问具体转化，只回答实际观察过的曝光、互动、反馈和刊发情况，不虚构点击率、涨粉归因或转化率。

### W5：你提到评论和内容反馈的分级处理，具体是什么？

> 我参与的重点不是大规模社区审核，而是围绕已发布内容识别反馈类型和处理优先级。例如先区分事实纠错、普通意见、明显情绪表达、平台规则风险和需要升级协同的问题，再决定是记录观察、补充信息、调整内容，还是交由相应负责人处理。我的职责更接近反馈识别、分类和流程衔接，不会把自己包装成评论治理策略的最终负责人。

如果涉及敏感业务细节，统一回答：

> 具体响应口径和协同对象不便展开，但我可以讲通用的分类方法、升级原则和如何留痕复盘。

### W6：你在工作中看哪些数据？

> 我的正式工作更关注内容供给完成度、发布时效、不同平台的曝光与互动反馈、重点内容的传播表现，以及矩阵账号的执行反馈。我会用飞书表格和 Python 做清洗、分类和阶段汇总，目的是识别哪个环节存在供给缺口、内容不适配或执行异常。这里不涉及我独立负责 DAU、留存或商业转化，所以我不会把内容传播指标写成产品增长结果。

### W7：你做过矩阵账号运营吗？

> 做过。我参与多个官方账号和约 150 人素人号矩阵的日常协同，也对接过 30 多位本地 KOL / KOC。我的工作包括任务分发、内容要求说明、节奏协调、发布反馈收集和台账维护。这个过程中最重要的不是把任务发出去，而是让不同参与者理解统一目标，同时保留各平台和账号应有的表达差异。

不要说成“独立搭建并管理 150 人矩阵”，除非能够进一步证明管理权限和完整运营责任。

### W8：举一个跨团队推进的例子。

> 以专题内容协同为例，目标通常来自阶段传播需求，但素材、内容、审核、账号发布和外部创作者分别在不同角色手中。我会先把要求拆成选题范围、素材规格、审核节点、平台版本和交付时间，再逐项跟进；遇到内容不适配时，不只是退回，而是说明需要修改的是事实、结构、标题还是平台表达。最终我负责把各方状态收拢，确保审核、刊发、反馈和归档能够闭环。

可补充结果：2025 年通过该类协同推动 99 件团队稿件获相关专栏刊发。结果属于团队，个人贡献是流程衔接和质量把关。

### W9：你的工作体现了什么产品思维？

> 我没有把正式运营经历说成产品经理经历，但其中有三类可迁移的产品能力。第一，把模糊传播目标拆成可执行的内容和流程要求；第二，根据平台与用户差异做分发和表达取舍；第三，通过反馈、数据和异常问题修正规则。它与产品工作的共同点是问题定义、流程设计和验证，但我缺少的是在正式岗位中直接负责产品路线图和研发资源，这部分主要通过个人 AI 产品实践补足。

### W10：你参与内部 SaaS 验收时做了什么？

> 我是作为一线业务使用者参与上线前验收，不是系统产品负责人。我按真实业务流程走查功能，提交了 6 项分级问题，并把触发条件、操作路径和预期结果整理清楚。其中一个关键问题通过复现信息帮助开发团队较快定位，修复后我再按原路径验证。这个经历让我比较重视 Badcase 的可复现性：只说“不能用”没有价值，要把输入、步骤、环境和结果记录完整。

如果被追问“约 30 分钟定位”，准确表述为协助开发定位所用时间，不说成你本人 30 分钟修复。

### W11：工作中最有挑战的事情是什么？

> 最大挑战是同一项传播目标需要在不同平台、不同内容来源和不同协作角色之间保持一致，但又不能把所有内容处理成一个模板。我的处理方式是把不能变化的事实和规则，与可以变化的标题、叙事入口、素材和语气分开，再通过审核节点和发布反馈校正。这个经验也影响了我做笔润智谈：全局规则和个体偏好应该分层管理，不能全部塞进同一个 Prompt。

这个答案能自然连接 Memory 策略，比泛泛强调抗压更有效。

### W12：你做出的最明确结果是什么？

> 我更愿意分三种结果回答。供给侧，2025 年作为协同中间层推动 99 件团队稿件获得相关专栏刊发；分发侧，长期维护微博、今日头条、小红书及矩阵账号的稳定更新和反馈回收；机制侧，参与多轮内部运营验证和阶段复盘，根据结果识别薄弱环节并调整后续执行。前两项能证明稳定交付规模，第三项证明我不是只完成发布动作，也会根据结果修正方法。

不要主动使用“模拟演练”的具体业务名称、次数和区域排名；若业务面确有必要了解，可在确认保密边界后用“内部策略验证与复盘”说明。

> 两者业务对象不同，但底层工作有连续性。内容运营要求我判断一条内容为什么不合适，是事实错误、结构问题、平台表达问题、用户反馈问题还是流程异常；Agent 效果策略同样需要把坏结果归因到 Prompt、Context、Memory、工具或运行层。我的优势是既有真实内容质量判断经验，也把这套判断在笔润智谈中做成了 Prompt、Memory、Trace 和评测机制。迁移成立，但我不会把运营年限直接等同于 AI 产品年限。

> 正式工作保证正常交付，个人项目主要利用业余时间推进。对我来说，工作提供了真实的内容质量、协作和反馈场景，个人项目则让我把这些观察转化为产品机制并完成实现。两者有经验迁移，但数据、用户和系统边界是分开的，我不会把个人项目写成公司内部产品。

### W15：你是不是主要做执行，为什么现在想转产品策略？

### 三个可随时调用的工作案例

#### 案例 A：多平台内容适配

> 同一个城市主题需要覆盖微博、今日头条和小红书。我先固定核心事实与传播目标，再分别调整话题入口、标题信息量、叙事视角、篇幅和素材组合；发布后记录各平台反馈，判断是内容本身还是渠道表达需要调整。这个案例证明平台差异判断和反馈迭代。

## 十、场景题

### Q34：入职第一周收到大量 Badcase，你会怎么处理？

> 我不会立即逐条改 Prompt。第一步先确认产品目标和当前核心指标；第二步抽样建立问题分类树，区分高频、高风险和高价值任务；第三步选出能稳定复现的代表案例，关联模型、Prompt、工具、Memory 和 Trace；第四步与产品和算法确认优先级，先处理安全、错误执行和主链路失败；第五步建立一小批固定回归集，确保修复不会破坏正常样本。第一周的产出应该是问题地图、优先级和可复现样本，而不是若干没有验证的 Prompt 改动。

### Q35：某个 Prompt 版本离线分数提高，但用户留存下降，怎么办？

> 先怀疑指标是否代理错了，而不是先怀疑用户。拆分用户类型和任务类型，检查分数提升来自哪个维度，是否同时增加了输出长度、等待时间、模板化或修改成本。再看用户中断、重试、编辑和重复使用行为，并抽取真实任务复核。如果离线 Rubric 奖励了用户不需要的特征，就应该修正评测标准，而不是继续优化分数。

### Q36：怎样判断一个问题该改 Prompt、Memory 还是 Agent 策略？

> 如果同类任务在所有用户上都失败，优先检查 Prompt、Context 和模型能力；如果差异来自用户长期偏好，考虑 Memory；如果步骤选择、工具调用或恢复路径失败，改 Agent 策略；如果是确定性校验，用规则；如果风险和责任不能交给模型，就保留人工决策。原则是修复最接近根因的一层。

## 十一、对方可能进行的压力测试

### “你的项目是不是套壳？”

> 如果只是调用模型生成文本，我认为确实是套壳。我的工作重点在模型之外：如何定义写作质量，如何区分全局规则与个人偏好，如何让 Agent 失败时退出和人工接管，以及如何用评测与 Trace 复核策略。这些机制都可以通过产品和代码现场说明。同时我也承认 V2 还没有经过大规模生产验证。

### “这些用户数据是真的吗？”

> 我把口径分开记录：200+ 是体验覆盖，53 名是完成过真实写作任务的作者；V2 是 14 名内测用户和近 70 条完整任务样本。它们分别代表覆盖、完成任务和内测样本，不等同于留存或商业用户。我不会把这些数字合并成更大的用户规模。

### “你是不是只会写 Prompt？”

> Prompt 只是一个策略层。格式趋同是 Prompt 问题，个人偏好冲突是 Memory 作用域问题，批量查重失败是并发和兜底问题，步骤遗漏是 Agent 编排问题。我的判断标准是先归因，再选择修复层，而不是所有问题都加一句 Prompt。

### “为什么我们要招你，而不是有正式 AI 经验的人？”

> 有正式大厂 AI 经验的候选人在组织协作和规模上会比我强，这是事实。我的差异是同时具备内容质量判断、真实用户反馈和亲手把 Agent、Memory、Eval 做成可运行产品的能力。我对自己的边界也比较清楚，能区分什么是已验证、什么是本地实现、什么还需要生产数据。对于效果策略岗位，这种判断和诚实会减少很多无效优化。

## 十二、建议向对方反问

电话结束前优先问 3—4 个：

1. 这个岗位服务的是小红书哪一类 C 端 Agent，核心用户任务是什么？
2. 当前效果团队最主要的问题是 Prompt / Memory 策略、评测体系，还是线上 Badcase 规模化处理？
3. 该岗位能否直接接触脱敏后的真实 Trace、用户反馈和实验数据？
4. 外包员工在策略设计、实验和版本评审中的权限边界是什么？
5. 日常汇报对象、业务团队和绩效评价方分别是谁？
6. 劳动合同、工资、社保公积金分别由哪一主体承担？
7. 转正、续约或内部岗位申请是否有明确机制和历史案例？

不要先问小红书福利、员工折扣或“多久能转正”。先确认工作内容和数据权限。

## 十四、电话前 10 分钟速记卡

### 三个最强案例

1. 格式趋同 → 拆分逻辑与表达维度 → 调整 Prompt 规范；
2. 标题伦理 / 个人视角 → 不写入全局 Prompt → 按用户和作用域管理 Memory；
3. 查重失败 → 归因到并发和稳定性 → 重构失败兜底，完成 30 余次真实批量任务。

### 三个主动承认的边界

1. 没有一年正式 AI 产品岗位经验；
2. V2 尚未正式部署；
3. 评测链路已实现，但生产级人类校准和在线 A/B 尚未完成。

### 一句话方法论

> 先用用户任务定义“好”，再把 Badcase 归因到正确层级，用最小策略修复，并通过固定评测集和真实行为验证，而不是靠一次漂亮输出判断效果。
