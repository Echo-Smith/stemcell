# Agent 策略岗位｜面试复盘与标准回答库

更新时间：2026-08-13
适用方向：Agent 效果策略、AI 产品策略、Prompt / Memory 策略、模型评测、AI 产品运营
适用轮次：HR / HRO 沟通、业务初面、策略深挖、交叉面

## 一、这套回答库解决什么问题

目标不是背诵“完美答案”，而是在追问中稳定证明五件事：

1. 确实做过真实 AI 产品，而不是复述架构名词；
2. 理解 Agent、ReAct、RAG、Memory 和工具调用的基本原理与取舍；
3. 能定义输出好坏，知道 Eval 从样本、Rubric 到回归发布如何工作；
4. 能把 Badcase 定位到正确层级，采用最小策略修复并检查副作用；
5. 能作为效果 Owner 与产品、算法、工程和人工评审者共同推进。

### 必须主动守住的边界

- 正式岗位不是 AI 产品经理，不能回答成有一年以上正式 AI 产品经验；
- 没有投稿分母和可比基线，不能说提升投稿成功率；
- 已完成的是离线评测和候选冻结，Holdout 尚未完成；不能写成生产发布门禁、在线 A/B 或策略已上线；
- 输出级用户接受反馈不能换算成独立用户人数，也不能直接推导留存或业务增长；
- 被部门采用的是“核查较真”能力，不是整个笔润智谈成为公司级系统；
- 个人和双人项目不能包装成主导大型算法、产品和研发团队。

## 三、统一回答结构

### 1. 30 秒回答公式

使用：

`结论 → 项目映射 → 边界`

例：

> ReAct 是让模型在循环中交替判断下一步行动、调用工具并读取结果。在笔润智谈中，它适合资料不足时动态决定继续搜索还是进入写作；固定的事实核查和人工确认节点仍由 Pipeline 保证。我实现并使用了这一机制，但没有把它作为所有任务的默认方案。

### 2. 90 秒回答公式

使用：

`结论 → 场景 → 机制 → 证据 → 边界 / 反思`

### 3. 被问到不会的概念

不要猜，也不要只说“不知道”。使用：

> 这个概念我目前无法给出足够准确的定义，我先不凭印象回答。结合我做过的项目，我能确认的是……；如果岗位继续推进，我会在面试后补齐其标准机制、适用边界，并核对我项目中的实现是否真的符合这一概念。

## 四、开场与项目定位

### Q1：请做一个自我介绍。

#### 75 秒标准回答

> 您好，我目前有接近两年的内容平台、质量判断和跨团队协同经验。正式岗位是内容运营，但我长期处理的核心问题是：不同平台怎样定义好内容、作者反馈如何转成稳定规则，以及出现问题后如何判断是内容、流程还是系统原因。
>
> 今年 3 月，我从作者最困难的选题和构思环节出发，独立做了 AI 写作产品笔润智谈，覆盖热搜选题、写作、润色、查重和事实核查。2026 年 5—8 月，14 位作者借助产品完成 28 篇获栏目刊发的稿件，单个用户最高使用 20 余次；其中“核查较真”能力后来被部门采纳并拆分部署。
>
> 面试后我进一步把人工判断沉淀成离线评测链路：通过校准集、Rubric 盲评与仲裁、48 对开发集实验比较来源证据和个人风格策略。目前来源证据闸门已进入 Holdout，个人风格 Memory 因用户接受反馈下降没有默认启用。下一步需要补齐的是 Holdout、线上灰度和大团队协作，这也是我希望进入 Agent 效果策略岗位继续发展的原因。

#### 回答要求

- 前 15 秒必须说清正式背景和目标岗位；
- 只讲一个主项目；
- 先讲 14 位、28 篇、20 余次，再补 200+；
- 明确离线 Eval 已经执行，生产发布与在线实验仍是成长项；不要把两者混为同一成熟度。

### Q2：为什么做笔润智谈？

> 我先发现的是业务问题，不是先决定做 Agent。部分作者想向固定栏目投稿，但原流程需要自己找选题、构思、撰文、检查，最困难的是选题和构思；同时，不同作者对标题、结构和表达方式又有个体差异。普通聊天模型可以生成一篇文章，但无法稳定处理实时资料、写作规范、个人偏好和失败回退，所以我把产品设计为从选题、检索、写作、润色到核查的工作流。

### Q3：这个产品到底是什么，不就是AI工具集吗？

> 如果只是把几个 Prompt 放在页面上，确实只能算工具集。笔润智谈的产品性主要体现在三处：第一，围绕作者完整任务组织功能，而不是让用户自己拼 Prompt；第二，检索材料有来源优先级、相关性过滤和冲突处理，不能无条件进入生成；第三，结果失败时区分资料、提示词、个人偏好和系统问题，并保留重试、人工修正和接管。当前它已经验证真实任务和重复使用，但还不能说已经形成成熟商业产品。

### Q4：项目最明确的结果是什么？

> 2026 年 5—8 月，14 位作者借助产品完成 28 篇获栏目刊发稿件，单个用户最高使用 20 余次，功能主要集中在热搜选题写作、润色和查重；累计体验规模超过 200 人。这个结果证明产品进入了真实投稿任务并出现重复行为，但因为没有完整投稿分母，我不会把它表述为投稿成功率提升。

### Q5：个人项目如何进入真实业务？

> 产品最初部署在个人服务器，主要供作者体验和完成写作任务。后来其中“核查较真”能力被部门认可，已从个人产品中拆分并部署到公司服务器。这证明一项能力完成了从个人探索到内部采用，但目前没有部门使用人数和效率变化数据，所以我不会扩大成整个产品已经公司级落地。

## 五、Agent 原理与架构

### Q6：什么是 Agent？

> 我理解的 Agent 不是“会聊天的模型”，而是围绕目标持续维护状态，能够规划或选择下一步、调用工具、读取观察结果，并在满足完成条件或退出条件时结束的系统。产品上要额外设计权限、失败恢复、人工确认、成本和可观测性，否则自主性越高，错误也越难控制。

追问“和 Workflow 的区别”：

> Workflow 的步骤主要由人预先定义，适合路径稳定的任务；Agent 可以根据状态动态决定下一步，适合路径不完全确定的任务。实际产品通常是混合方案，而不是二选一。

### Q7：什么是 ReAct？

> ReAct 可以理解为 Reasoning 与 Acting 交替进行的 Agent Loop。模型根据目标和当前观察判断下一步，选择行动或工具，读取工具返回的观察，再继续判断，直到给出结果或触发退出条件。它的价值是让模型根据中间结果动态调整路径，而不是一次生成完整答案。

项目映射：

> 在笔润智谈中，如果任务资料不足，Agent 可以先检索，读取结果后再判断是否补查、调用知识库或进入写作。但关键事实核查、审校和人工确认不应完全依赖模型自由选择，因此我同时保留固定 Pipeline。

常见追问：

- 如何避免死循环：迭代上限、全局超时、Token 预算、连续模型失败断路器、用户取消和人工接管；
- ReAct 的代价：调用次数、延迟和成本提高，路径也更难复现；
- 不适用场景：步骤明确、错误成本高、需要确定性审计的任务。

### Q8：为什么同时使用 Pipeline 和 ReAct？

> 我用任务确定性和错误成本做选择。解析任务、事实核查、审校和关键确认不能随意跳过，使用固定 Pipeline；资料是否充分、下一步调用哪个搜索或知识工具具有不确定性，可以交给 ReAct。这样既保留关键流程的可控性，也避免把所有复杂情况写成大量分支规则。

### Q9：什么是 Function Calling / Tool Use？

> 模型不直接执行外部能力，而是按预先定义的工具名称和参数结构发出调用请求，系统校验参数、执行工具，再把结果返回模型。产品上不能只看“是否调用”，还要评估工具选择是否正确、参数是否正确、结果是否被正确使用，以及失败时是否降级或转人工。

### Q10：Agent Loop 如何退出？

> 至少有四类条件：任务完成；用户主动取消；资源或时间达到上限；连续失败或风险触发停止。我的项目中还考虑了断连暂停、迭代上限、人工确认超时和有限修复次数。退出不是工程细节，它决定用户会不会陷入无限等待或不可控消耗。

### Q11：Multi-Agent 的意义是什么？

> Multi-Agent 只有在角色目标、输入输出和责任边界确实不同的情况下才有意义。例如研究、写作和审校分别产出资料简报、稿件和审校结论，便于独立回退和人工介入。如果只是把一个 Prompt 拆成多个角色名称，却没有不同状态、权限或评价标准，就只是增加调用成本。

## 六、RAG、知识库与搜索策略

### Q12：RAG 是什么？为什么需要？

> RAG 是在生成前检索外部知识，把相关材料作为上下文提供给模型。它可以补充模型参数中没有或可能过期的信息，也便于保留来源；但检索到内容不代表内容正确，仍要处理相关性、权威性、冲突、权限和 Prompt Injection。

项目映射：

> 笔润智谈把用户提供材料设为最高优先级，知识库用于写作规范和参考素材，联网搜索补充实时事实、讨论和案例。模型常识只用于连接和解释，不用于凭空制造事实。

### Q13：接入了哪些搜索工具？为什么不是越多越好？

> 当前写作链路可接入知识库、知乎站内 / 全网、Tavily、微博智搜和腾讯新闻或较真核查等来源。不同来源承担不同任务：知识库提供写作规范和历史素材，知乎补充讨论和案例，微博补充实时语境，新闻与较真更偏事实核验。来源越多会增加重复、冲突、延迟和成本，所以必须先按任务规划检索，而不是全量调用。

### Q14：搜索上限和停止条件怎么设计？

> 先从任务中提取 1—3 个检索 query。轻研究模式下，每个 query 只取少量高相关结果，经过去重和价值过滤后，目标是获得覆盖核心事实、至少能支撑主要论点的独立材料，而不是追求最大条数。当前设计中常规写作总素材量控制在约 8—10 条，再按 strong、medium、weak、conflict 分类。
>
> 停止条件包括：核心事实已有独立来源支撑；新增搜索不再带来新的事实或观点；达到时延或调用预算。如果关键事实仍缺失，就不应假装资料充分，而应继续补查、向用户追问，或用不确定表达并提示人工核验。

### Q15：多源信息如何清洗与冲突校准？

> 先按 URL、标题和语义近似去重，再按与任务相关性、信息价值、来源质量和发布时间排序。用户材料与外部来源冲突时不直接混写：外部权威来源明显更强时标记冲突；双方都无法确认时，降级为条件性表达或停止写入确定事实。冲突不是让模型“投票”，而是保留来源和不确定性供后续判断。

### Q16：慢接口超时后直接丢弃吗？

> 不能把所有超时都简单等价为可丢弃。要判断它承载的是补充信息还是关键事实：如果其他来源已覆盖核心信息，可以降级继续并记录来源缺失；如果缺失会影响事实判断，就应该停止成稿、补查替代来源或提示人工确认。系统可以设置单源超时和总预算，但完整性是业务决策，不是纯技术超时逻辑。

### Q17：如何评价检索效果？

> 重点不是返回多少条，而是最终有多少条可用于任务。可以看可用材料率、首次命中率、相关性、来源完整度、冲突率、每篇文章使用的有效来源数，以及 P50 / P95 延迟。在线还要观察资料不足导致的人工补充、任务中止和事实修改情况。

## 七、效果定义与 Eval

### Q18：当前到底有没有评测体系？

> 有，但必须分清离线评测和生产闭环。目前我已经实际运行一套离线策略评测：先用 20 条校准集暴露评分分歧，经业务负责人仲裁和多轮双模型盲评冻结五维 Rubric V5；再对来源证据闸门和个人风格 Memory 做 48 对开发集单变量实验，记录通过率、硬失败、修改负担、成对偏好和输出级用户接受反馈。当前候选版本已冻结，32 对 Holdout 已生成但尚未完成盲评；因此可以说已做到候选冻结阶段，不能说已形成生产发布门禁、在线 A/B 或持续线上 Eval Loop。

这是必须统一的口径。不要再回答“没有评测”，也不要把 Holdout 待评说成上线结论。

### Q19：怎样定义一篇润色结果是好的？

> 我会先定义“保持什么”和“改变什么”。润色必须保持原意和关键事实，在此基础上改善结构连贯、段落功能、论证完整和语言可读性；同时满足栏目篇幅与表达边界。不能因为语言更华丽就改变作者立场，也不能把所有作者改成同一种模板。

建议 Rubric：

| 维度 | 判断问题 | 是否硬门槛 |
| --- | --- | --- |
| 原意保持 | 是否改变观点、事实和态度 | 是 |
| 事实可靠 | 是否新增无依据事实 | 是 |
| 任务合规 | 篇幅、格式、栏目要求是否满足 | 是 / 规则判断 |
| 结构改善 | 段落作用和论证顺序是否更清楚 | 否 |
| 表达自然 | 是否减少病句、重复和模板化句式 | 否 |
| 作者风格 | 是否保留用户可辨认的表达偏好 | 否 |
| 可用程度 | 用户需要多少人工修改才能提交 | 关键结果指标 |

### Q20：规则是谁制定的，凭什么有效？

> 规则来源于获刊发素材的结构共性、作者与内容审核反馈，以及历史正反案例。我先把经验拆成任务符合度、事实可核验性、结构与推理、风格一致性和可直接使用程度五个维度，再设置事实编造、改变原意等不可被平均分抵消的硬失败。首轮 20 条校准中，两名模型评测者的通过一致率只有 60%，所以没有直接冻结；业务负责人仲裁争议后持续修订规则，直到 V5 的两模型独立盲评通过结论一致率达到 100%，再用预先封存的人工黄金结论处理硬失败标签冲突。它证明规则经过了分歧校准，但仍不是行业权威标准或全量双人工金标。

### Q21：如果让你从零搭建评测集，怎么做？

> 我已经按这个流程做过一轮。先按选题、写作、润色、查重和异常输入分层，从历史任务、Badcase 与边界场景形成校准集；再冻结输入、来源、预期行为、难度、风险标签和硬门槛。20 条校准集用于修订 Rubric，不用于证明策略效果；Rubric 稳定后，再构建 48 对开发集和 32 对 Holdout。开发集用来筛策略和找失败，候选冻结后才运行 Holdout，不能看过 Holdout 再回头调参。后续线上新 Badcase 进入候选池，经过归因和复核后再决定是否并入回归集。

### Q22：Rubric 如何避免拍脑袋？

> 一是每个维度写清定义、1/3/5 分锚点和正反例；二是把事实编造、未来写成已发生、改变原意等设为硬失败，不能被结构和文风高分抵消；三是让不同评测者盲评同一批样本，用通过冲突、硬失败冲突和维度差异暴露规则歧义；四是通过业务仲裁把分歧变成下一版规则，不覆盖旧版本；五是加入修改负担和输出级用户接受反馈，检查高分是否真的对应可用。笔润智谈的 Rubric 从 V1 到 V5，就是因为前几轮一致性和硬失败冲突不达标而持续迭代。

### Q23：人评和机评如何分工？

> 规则负责格式、哈希、字段完整性等确定性校验；模型评测者按 Rubric 做可规模化的语义盲评；业务负责人负责标准制定、争议仲裁、高风险边界和黄金结论。笔润智谈首轮两个模型的一致率只有 60%，说明模型不能自己生成、自己评分、自己宣布上线；后续 V5 仍保留了原始硬失败冲突，并只允许用评测前已封存的人工黄金结论裁决。生产中还需要人工抽检高风险、低置信、版本分歧和线上投诉样本。

### Q24：什么是 LLM-as-Judge？有什么偏差？

> LLM-as-Judge 是让模型按照固定 Rubric 对输出评分或比较，适合规模化评价相关性、逻辑和风格。常见偏差包括长度、自身风格、位置、提示词敏感和评分尺度漂移。我在项目中使用随机化方案甲乙、隐藏模型与策略身份、不同模型家族独立盲评、硬失败门槛和人工仲裁来降低偏差；看过仲裁口径的复评会单独标记为 `calibrated_recheck`，不能冒充独立盲评。

### Q25：自动化评测 Loop 是什么？

> 一个完整 Loop 包括版本和样本冻结、批量运行、盲化评审、与基线比较、失败聚类、人工复核、候选冻结、Holdout、发布门禁、灰度观察和线上 Badcase 回流。我现在已完成到候选冻结和 Holdout 材料生成：48 对开发集用于筛选策略，32 对 Holdout 待一次性盲评。还没完成的是 Holdout 结论、线上灰度与持续回流，所以它是已运行的离线 Loop，不是成熟生产 Loop。

### Q26：如何设计 C 端 Agent 指标？

> 主指标回到用户任务，例如有效任务完成率或用户确认完成率。效果指标包括相关性、事实正确、工具调用正确、个性化匹配和人工修改量；行为指标包括完成、中断、重试、接管和重复使用；护栏包括安全违规、错误执行、P95 延迟、成本和投诉。不同任务必须分层，不能用一个总满意度覆盖高风险工具执行和普通聊天。

## 八、Badcase 归因与策略修复

### Q27：Badcase 怎么分类？

> 我先按根因层级分类：输入与意图、Context / 检索、Prompt、Memory、Planning / Tool、模型输出、系统运行和交互预期。然后关联任务、模型版本、Prompt 版本、检索结果、工具参数和 Trace，先确认能否稳定复现，再选择最接近根因的一层修复。

### Q28：Badcase 怎么定优先级？

> 用风险、影响用户数、主链路阻断程度、发生频率和修复成本综合判断。安全、错误执行和事实性错误优先于轻微风格问题；主链路无法完成优先于局部体验瑕疵。高风险低频问题不能只按频次排后，高频但影响轻的问题可以批量治理。

### Q29：讲一个模板化表达的案例。

> 用户反馈润色后逻辑更清楚，但措辞有时不像本人。我把问题假设为“结构化个人风格 Memory 能否改善接受度”，保持模型、任务和来源不变，只比较通用策略与增加个人风格 Memory 的两个版本。开发集两组通过率都是 100%，但实验组的输出级用户接受率从对照组 87.5% 降到 50%，平均修改负担也略有上升。这说明离线质量通过不等于用户喜欢，Memory 可能过度强化偏好或让表达变得刻意，所以我没有把它默认启用，而是保留为待进一步分用户验证的候选能力。边界是每组只有 24 个开发集输出，不能宣称统计显著或线上留存下降。

### Q30：讲一个检索资料不足或过期的案例。

> 在历史 Badcase 中，材料不足或与用户陈述冲突时，模型仍可能补写负责人原话、进度或数字。我没有只加一句“不要编造”，而是把它定义为来源证据闸门：关键事实必须有冻结材料支持，缺失或冲突时追问、显式降级或拒绝确定性成稿。开发集对照组和实验组各 24 个输出，实验组通过率从 75% 到 100%，硬失败从 5/24 降到 0，输出级用户接受率从 37.5% 到 75%，平均修改负担也下降，因此进入 Holdout。当前 32 对 Holdout 还没完成盲评，所以这仍是开发集观察，不是上线效果结论。

### Q31：讲一个工具或运行层案例。

> 批量查重出现并发失败时，问题不在内容质量，而在任务队列和外部调用稳定性。我按任务批次、失败状态和响应时间复现，增加并发控制、超时与失败兜底，并保护人名、数字、时间和否定事实不被错误改写。后续在 30 余次真实批量任务中，出现过单次 1500+ 条文本在 5 分钟内返回的记录。这里证明的是任务链路稳定性，不是模型写作效果。

### Q32：如何判断该改 Prompt、Memory 还是 Agent 策略？

> 同类任务对所有用户都失败，优先检查 Context、Prompt 和模型能力；只有特定用户长期偏好不同，考虑 Memory；步骤选择、工具调用、重试或退出路径失败，修改 Agent 策略；确定性格式问题用规则；高风险和责任边界问题保留人工确认。原则是修复最接近根因的一层。

## 九、Prompt 策略

### Q33：你怎么调 Prompt？

> 我遵循“复现—归因—单变量修改—成对比较—候选冻结”的流程。先冻结输入、模型、来源和 Memory，确认问题稳定存在；再判断它是否真是 Prompt 根因。若是，把模糊要求改成可判断的约束，每轮只改变一个主要变量，并随机化方案甲乙做盲评。来源证据闸门就是按这个方式与无闸门版本比较；个人风格 Memory 也因用户接受反馈变差而没有默认启用。最后记录 Prompt、运行器、数据集和输出哈希，避免看完结果后改口径。

### Q34：为什么不能看到一个错误就加一句Prompt？

> 因为错误可能来自资料、记忆、工具或交互，而且 Prompt 约束会互相影响。针对单个样本不断加规则容易过拟合，Prompt 变长还会增加冲突和模型忽略关键要求的概率。策略优化应该先聚类同类问题、判断根因，再做最小修复。

### Q35：Prompt调优如何验证没有副作用？

> 先让开发集同时覆盖原 Badcase、相邻任务、正常样本和异常输入，除目标维度外，还看事实硬失败、修改负担、成对偏好和用户接受反馈。开发集只负责筛选；选中候选后冻结案例、来源、Prompt、Memory 和运行器，再用未参与调参的 Holdout 验证。若目标指标提高但用户接受或其他任务退化，就不默认启用；个人风格 Memory 的决策就是一个实际例子。

### Q36：什么是 Context Engineering？

> Prompt 是模型看到的指令，Context Engineering 关注一次任务中模型到底看到了哪些信息、顺序、来源、状态和工具结果，以及哪些内容不应进入上下文。笔润智谈会区分用户材料、外部资料、冲突信息、写作规范和个人偏好，避免全部混成一段，也通过摘要控制长任务上下文。

## 十、Memory 策略

### Q37：Memory 和普通聊天历史有什么区别？

> 聊天历史是最近交互记录，Memory 是经过选择、带来源和作用范围、用于未来任务的状态或偏好。不是所有历史都应该长期保存。产品需要定义写入、召回、冲突、过期、修改和删除机制。

### Q38：个人风格为什么用 Memory，不继续改全局 Prompt？

> 全局 Prompt 应承载所有用户共享的写作要求；个人对标题、语气和表达边界的偏好不具有普遍性。写进全局规则会把一个人的价值判断错误施加给所有人，因此更适合按用户和任务范围管理，并允许用户修改或删除。

### Q39：如何避免 Memory 污染？

> 一次性内容默认不进入长期记忆；写入时保存来源、置信度、出现次数和适用范围；冲突偏好不直接覆盖，必要时请用户确认；敏感信息和低置信推断不自动保存；用户可查看、修改和删除。召回时还要限制数量和相关性，避免旧偏好压过当前明确指令。

## 十一、团队协作与岗位理解

### Q40：你过去主要独立搭建，如何适应多团队协作？

> 我的正式 AI 项目协作规模确实有限，这是我的短板。可以迁移的基础有三类：内容工作中长期在作者、审核、平台和业务部门之间对齐标准；内部 SaaS 验收时能把问题整理成触发条件、复现路径和预期结果交给研发；HearHer 是双人协作，需要共同收敛范围和交付。进入正式团队后，我会把个人项目中隐性的判断转成共同资产：目标指标、评测集、Rubric、策略变更单和回归报告，让不同角色依据同一标准协作。

### Q41：Agent策略产品运营在团队中做什么？

> 它不是单纯执行 Prompt，也不是替代产品经理或算法。这个角色应对 Agent 效果闭环负责：和产品确认用户任务和优先级；把“好”定义成评测集、Rubric 和指标；和 Prompt / 算法同学选择修复策略；和前后端确认 Trace、版本、灰度和回滚能力；组织人工评审和线上 Badcase 回流，最终输出可复核的策略结论。

### Q42：产品、算法、后端意见冲突怎么办？

> 先把争论从方案偏好转成共同目标和证据。明确用户任务、主指标、风险护栏和当前 Badcase；让不同方案在同一评测集或灰度条件下比较。无法短期验证时，优先选择可回滚、影响范围小的方案。策略 Owner 的职责不是坚持自己的 Prompt，而是让决策有统一口径并能复盘。

### Q43：如果入职第一周收到大量Badcase，会怎么做？

> 先确认核心用户任务和现有指标，再抽样建立问题分类树；关联模型、Prompt、Memory、工具和 Trace，选出高风险、高频和主链路阻断问题；建立一小批可复现回归样本，与产品、算法和工程确定优先级。第一周的交付应是问题地图、代表样本、责任层级和验证计划，而不是几十条未经回归的 Prompt 改动。

## 十二、压力题

### Q44：你是不是只会用 Codex 搭产品？

> Codex 提升了实现速度，但需求、流程、技术选择、验收和结果责任由我承担。比如资料不足需要改检索策略，模板化需要拆分全局规范和个人偏好，并发失败需要调整运行层，这些判断不能由生成代码替代。我会阅读和验证生成结果，也会明确自己目前不能独立完成底层模型训练。

### Q45：为什么简历写了ReAct却答不上来？

> 这是我本次面试暴露出的真实问题：项目实现用了这一机制，但我没有把工程实现上升为可清楚表达的原理与取舍。面试后我重新梳理了 Agent Loop、行动—观察循环、退出机制和适用边界，也把原则设为：今后简历中出现的每个术语，都必须能回答是什么、为什么使用、在哪里使用、何时不使用以及怎样验证。

如果再次被同一公司追问，诚实复盘比试图掩饰更可靠。

### Q46：你的评测体系是不是面试包装？

> 如果我只拿一份方案文档说做过 Eval，确实属于包装。但现在可以核验的不只是代码结构：有 20 条校准集、多个版本的 Rubric、盲评与人工仲裁记录、48 对开发集策略实验、候选冻结记录，以及 32 对 Holdout 输出。来源证据闸门和个人风格 Memory 也据此做出了不同候选决策。边界同样明确：Holdout 尚未完成，没有在线 A/B、生产发布门禁或大规模团队运行经验，所以我能证明的是一套实际跑过的离线评测与策略决策，不是成熟生产平台。

### Q47：为什么要招你，而不是正式做过Agent策略的人？

> 有正式生产经验的候选人在大规模线上实验和组织协作上更强，这是事实。我的差异是能把真实内容质量判断转成可执行的评测资产，并真正让策略接受失败：Rubric 不达门槛就继续迭代，个人风格 Memory 的用户接受反馈变差就不默认上线，来源证据闸门则进入 Holdout。我同时具备业务场景、作者反馈、独立产品交付和工程验证能力，适合需要从模糊问题快速建立评测与候选策略的初中级岗位；如果岗位要求直接负责成熟大规模线上 Benchmark，我仍有差距。

### Q48：你接受外包吗？

> 我会根据实际工作价值判断，而不是只看办公地点或品牌。重点确认能否接触真实 Trace、用户反馈和实验数据，是否参与策略和评测设计，绩效与汇报主体是否清楚，以及合同、薪资、社保和项目结束安排。如果只是执行 Prompt 或机械打分，长期价值有限；如果能形成真实效果闭环，我愿意认真评估。

## 十三、策略场景题

### S1：离线评测分数提高，但用户留存下降，怎么办？

> 先检查离线指标是不是奖励错了特征，而不是先认为用户“不理解好结果”。拆分用户和任务类型，确认分数提升来自事实、结构、风格还是长度；再看中断、重试、编辑、接管和重复使用行为，抽取真实任务人工复核。常见情况是 Judge 偏好更长、更完整的答案，但用户承担了更高阅读和修改成本。如果代理指标与用户价值背离，应调整 Rubric 或权重，而不是继续追求离线总分。

### S2：Judge 认为通过，人工认为不可用，怎么处理？

> 先保留分歧样本并定位分歧维度：是 Rubric 定义不清、评分锚点不足、Judge 偏差，还是人工标准不一致。高风险样本以人工结论为准；普通样本由第二评审复核。随后修订 Rubric、补正反例，并在固定分歧集上重新校准。不能通过换一个 Judge 直到得到想要的结论。

### S3：线上 Badcase 无法稳定复现，怎么办？

> 先补齐模型版本、Prompt 版本、温度、上下文、Memory、工具返回、时间和用户状态，尽可能重放原 Trace。若仍无法复现，将其标记为低复现但保留风险，不直接凭单例改全局策略；可以增加监控和相邻条件测试，等待同类样本聚类。高风险问题即使低频，也可以先通过规则或人工确认降低暴露面。

### S4：新 Prompt 修复了目标问题，却使其他任务变差，怎么办？

> 说明修改作用范围过大或 Rubric 只覆盖了目标样本。先回退发布，再判断是否应该缩小到特定任务模板、用户群或触发条件；如果问题本质是个人偏好，改用 Memory；如果是确定性约束，改用规则。最后补充受影响的正常样本到回归集，避免同类副作用重复发生。

### S5：模型和工具都执行正确，用户仍然不满意，如何归因？

> 技术正确不等于产品成功。需要检查任务是否定义错了、结果是否符合用户心智、等待过程是否可预期、是否给出修改和接管能力，以及输出是否增加了阅读或确认成本。此类问题应归入交互预期或价值定义层，而不是继续修改工具调用。

## 十四、三个必讲案例卡

### 案例一：模板化表达

`用户反馈逻辑改善但不像本人 → 提出结构化个人风格 Memory 假设 → 24 对开发集单变量实验 → 通过率持平但输出级用户接受率 87.5%→50% → 暂不默认启用 → 等待分用户与 Holdout 验证`

证明：用户判断、Prompt / Memory 边界、指标冲突下不追求“功能一定上线”。

### 案例二：检索材料不足或过期

`无来源事实与材料冲突 → 设计来源证据闸门 → 24 对开发集成对实验 → 通过率 75%→100%、硬失败 5/24→0、输出级用户接受率 37.5%→75% → 候选冻结 → 进入 32 对 Holdout`

证明：Context / Prompt 归因、单变量实验、硬失败治理与发布纪律。

注意：开发集每组 24 个输出，不做统计显著性或上线效果结论。

### 案例三：批量查重失败

`批量任务失败 → 根据任务状态与时延定位并发 / 工具层 → 加队列、超时、失败兜底和事实保护 → 30 余次真实批量任务验证，单次 1500+ 条文本在 5 分钟内返回`

证明：不是所有坏结果都改 Prompt、运行稳定性与回归意识。

## 十五、技术原理速查

| 概念 | 一句话原理 | 项目映射 | 主要边界 |
| --- | --- | --- | --- |
| Agent | 围绕目标维护状态、决定行动、调用工具并在条件满足时退出 | 动态检索与工具调用 | 自主性增加成本和不可控性 |
| Agent Loop | 目标—行动—观察—更新状态的循环 | 搜索后决定补查或写作 | 需要预算、超时和迭代上限 |
| ReAct | Reasoning 与 Acting 交替的 Agent Loop | 根据资料充分度选择工具 | 不适合所有固定高风险步骤 |
| Workflow / Pipeline | 人预先定义步骤和分支 | 任务解析、核查、审校、人工确认 | 灵活性较低但可复现 |
| Tool Use | 模型输出结构化调用，系统执行后返回结果 | 搜索、知识库、核查、查重 | 要校验工具选择、参数和结果 |
| RAG | 检索外部材料并作为生成上下文 | 写作规范、历史素材、实时资料 | 检索内容不等于真实或相关 |
| Rerank | 对候选材料重新排序以提高前列可用性 | 知识片段价值排序 | 需要与实际任务指标校准 |
| Prompt Engineering | 设计模型指令、约束、示例和输出格式 | 写作、润色、核查提示策略 | 易过拟合，约束可能冲突 |
| Context Engineering | 管理一次任务中模型看到的信息和状态 | 用户材料、外部资料、冲突、规范分区 | 上下文长度与噪声会影响效果 |
| Memory | 把经过筛选的状态或偏好跨任务保存和召回 | 用户标题与表达偏好 | 污染、过期、冲突和隐私风险 |
| Multi-Agent | 将不同目标和责任拆给多个 Agent 协作 | 研究、写作、审校 | 无真实边界时只是增加调用 |
| Trace | 记录一次任务的版本、步骤、工具、时延和错误 | 问题回溯 | 记录不等于形成决策闭环 |
| Eval | 用固定样本、标准和过程比较效果 | 20 条校准、48 对开发集、32 对 Holdout | Holdout 待评，不能写生产闭环 |
| Rubric | 将“好”拆成可解释维度和评分锚点 | 五维 Rubric V1—V5 与硬失败门槛 | 模型双评不等于双人工金标 |
| LLM-as-Judge | 让模型按 Rubric 评价模型输出 | 不同模型家族独立盲评与分歧报告 | 长度、自偏好、位置与尺度偏差 |
| Regression | 修改策略后回放固定样本检查修复与副作用 | 单变量成对实验、版本与哈希冻结 | 固定集也会过拟合，需 Holdout 和线上样本 |
| A/B Test | 同期随机分流比较两个策略的因果效果 | 当前尚未完成 | 需要足够样本和明确指标 |

## 十六、反问面试官

业务面优先选择三题：

1. 当前 Agent 最重要的用户任务和效果主指标是什么？
2. 团队现有 Badcase 是按什么分类，最大的未解决问题在哪一层？
3. 离线 Eval、人工评审和线上实验现在分别由谁负责，如何形成发布门禁？
4. 该岗位能否看到脱敏后的 Trace、版本信息、真实用户反馈和实验数据？
5. 策略产品、Prompt 调优师、算法和后端之间的决策边界是什么？

外包 / HRO 另外确认：合同主体、薪资结构、社保公积金、考勤、绩效方、项目期限和项目结束安排。

## 十七、训练方法

### 第一轮：准确性

- 逐个技术术语回答“是什么、为什么、项目中哪里用、何时不用、如何验证”；
- 每题先说结论，控制在 30 秒；
- 回看项目代码或文档，删除无法解释的术语。

### 第二轮：追问

每个主问题连续追问三层：

1. 为什么？
2. 具体怎么做？
3. 如何证明有效、有什么局限？

### 第三轮：压力与打断

- 随机从中间问题开始；
- 要求 20 秒、60 秒和 2 分钟三种长度；
- 故意加入反驳：“这不是套壳吗？”“没有 A/B 怎么证明？”“为什么不是规则？”；
- 练习承认边界后继续给出可验证证据。

## 十八、发布禁区

以下表述不得使用：

- “提升了投稿成功率”；
- “建立了成熟自动化 Eval 平台”；
- “整个笔润智谈被公司采用”；
- “主导算法、产品、前后端大团队”；
- “LLM Judge 可以替代人工”；
- “多源搜索能确保事实绝对准确”；
- “用了 ReAct 所以一定比 Workflow 更智能”；
- “200+ 用户证明产品留存或商业价值”。

正确原则：

> 已完成的实现、离线验证、真实用户行为、内部采用和业务结果分别陈述；不知道的原理不猜，缺少的指标不补，未来设计不写成既有成果。
