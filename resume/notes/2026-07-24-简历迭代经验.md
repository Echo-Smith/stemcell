# 简历迭代经验：从“堆经历”到“可验证的岗位论证”

更新时间：2026-07-24

这不是一份新的简历模板，而是多轮版本修改后沉淀出的判断标准。旧简历只提供事实线索，不提供结构、顺序和措辞上的权威。

## 一、最重要的结论

一份有效简历不是经历清单，而是对一个命题的证明：

> 为什么这个人能够胜任这个具体岗位，而且其能力已经通过真实行为和结果被验证？

因此，写简历的顺序应该是：

**目标岗位 → 核心能力命题 → 证据选择 → 事实核验 → 项目叙事 → 排版导出**

而不是：

**找到旧简历 → 换几个关键词 → 补技术名词 → 压成一页**

## 二、这些迭代已经证明有效的做法

### 1. 一份简历只能有一条主角色线

过去的版本在内容运营、增长、AI 产品、效率工具、企业 Agent、C 端 AI 之间来回切换，容易让招聘方不知道候选人究竟要解决哪类问题。

较有效的表达方式是：

- 先确定主角色，例如“有内容业务经验、能独立构建并验证 Agent 产品的 AI 产品经理”；
- 内容运营是问题来源和业务优势，不是与 AI 产品并列争夺篇幅的第二职业；
- HearHer、SubBuddy、LuminBuddy 根据岗位需求承担不同证据角色，而不是每个项目平均用力。

### 2. 产品问题必须先于技术架构

项目不能从 “Multi-Agent、RAG、MCP、ReAct” 开始。招聘方首先需要知道：

- 谁在什么工作里遇到了什么阻塞；
- 现有工具为什么不够；
- 你做了什么关键产品判断；
- 系统改变了哪一个工作流；
- 结果如何被验证。

技术架构的价值在于解释关键决策和能力边界，而不是展示名词密度。

对 LuminBuddy 尤其如此：它未来最有价值的叙事不是“增加了多个 Agent”，而是“把选题、研究、写作、审校和发布组织为一个可委派、可追责、可人工接管的编辑部工作流”。

### 3. 旧简历是证据池，不是母版

不同版本相互复制，已经产生了数字漂移、角色漂移和措辞膨胀。正确做法是先把事实拆成最小单位：

- 发生了什么；
- 谁完成的；
- 时间与样本范围；
- 数据来源；
- 能否展示证据；
- 哪些只是推断；
- 哪些版本彼此矛盾。

只有完成这一步，才能重新组合成不同岗位的简历。

### 4. 项目归属写准确，可信度反而更高

“个人项目”“团队项目”“本人负责”“团队共同完成”“外部专业支持”应明确区分。

过去最成熟的一次改进，是在审查优化 V3 中主动标记：

- LuminBuddy 属于个人项目；
- HearHer 属于团队项目；
- 个人负责的产品、评测或实现范围；
- 数据是在 MVP、合成样本或有限用户条件下得到的。

这些限制不会削弱简历。相反，它们让面试官更愿意相信其余成果。

### 5. 指标必须带条件，不能只剩漂亮数字

每个指标至少要回答其中大部分问题：

- 分母是什么；
- 样本量多少；
- 时间窗口多长；
- 基线是什么；
- 测试环境是什么；
- 是线上真实用户、种子用户还是内部样本；
- 是个人直接影响、团队结果还是相关性；
- 是否有失败样本和质量护栏。

目前 LuminBuddy 的高风险口径包括：

- “9 个场景”实际更像 9 个测试用例，且分布在写作、润色、缩写、对话四类任务；
- “6 次自动修复全部成功”与报告字段逻辑存在不一致，不能直接使用；
- “单次成本 0.0031 元”依赖旧价格和输入输出比例假设，不能当作长期稳定事实；
- “53 名用户、3 名真实作者、7 篇采用文章、60 次提交/25 次采用”可能都真实，但必须说明它们之间的层级和统计范围。

### 6. 团队结果不等于个人影响

“项目获得 200+ 提案、进入 14 强”可以证明项目质量和竞争结果，但不能自动证明某个功能是本人独立完成。更稳的写法是把结果拆成：

- 团队最终结果；
- 本人承担的决策与交付；
- 个人工作的证据；
- 两者之间能够被解释的关联。

### 7. Demo、MVP 与生产系统必须区分

公开演示、有限用户试用、竞赛 MVP、内部评测和生产落地是不同强度的证据。不能仅因为系统可以运行，就使用“规模化落地”“稳定生产”“企业级”等结论。

但 MVP 并不弱。如果能够展示：

- 为什么这样定义最小闭环；
- 如何选择评测集；
- 发现了什么失败模式；
- 如何加入人工接管、权限和成本约束；
- 哪些结论尚不能推广；

它对 Agent 产品岗位仍然是很强的证据。

### 8. “能写代码”要通过产品判断体现

单纯罗列 Python、Go、TypeScript、MCP、模型名称，无法证明岗位要求中的动手能力。

更有说服力的是：

- 为了验证什么假设，手搓了怎样的 Harness；
- 为什么选择流水线、ReAct 或多 Agent；
- 哪些步骤可并行，哪些必须串行；
- token、延迟、可靠性之间如何权衡；
- 如何观测失败、回滚和人工接管；
- 实验结果如何改变产品设计。

### 9. 简历也是面试契约

每一句强结论都应该能在面试中展开为：

**背景 → 决策 → 取舍 → 行动 → 结果 → 局限 → 下一步**

如果一句话无法被追问三层，或者追问后只能回答“这是模型写的”“大概如此”，它就不应该出现在简历里。

### 10. 人味来自具体决策，不来自口语化包装

机械地把每个 bullet 写成相同的“通过……实现……提升……”会让简历像模板。真正的人味来自：

- 一个真实的用户事件；
- 一次失败或冲突；
- 一个反直觉决策；
- 一个明确约束；
- 一项本人坚持的取舍。

少用“赋能、闭环、沉淀、抓手”等泛化词，多写实际行为和判断。

## 三、面向 Kimi Agent 协作岗位的新判断

这个岗位需要的不是泛泛的“做过 AI 产品”，而是四类集中证据：

1. **Harness 能力**：能快速构建并比较协作编排方案。
2. **协作产品判断**：理解任务、人员、信息、权限与决策如何在组织中流动。
3. **Agent-native 工作方式**：本人长期把 Agent 当合作者，并形成可展示的工作系统。
4. **协作基础设施理解**：能解释 MCP、A2A、ACP、委派策略、冲突解决、人工介入和信任边界。

当前简历已经有的优势：

- 内容业务与真实工作流经验；
- 能独立实现可运行的 AI 产品；
- 有评测、成本、可观测性和边界意识；
- LuminBuddy 天然具备向编辑部协作系统演进的业务基础。

当前仍缺少的核心证据：

- 真正的 agent-agent 任务协议，而不只是单 Agent 调工具；
- 角色分工、任务委派、冲突解决与权限控制；
- 人类编辑在关键节点如何批准、改派或接管；
- 多 Agent 相比单 Agent/固定流水线的效果、成本和失败率对照；
- 协作界面如何呈现任务、产物、决策和责任；
- 一段能现场展示的“一个人带着 Agent 编辑部完成真实任务”的端到端工作流。

因此，下一版简历不应急着添加 “Multi-Agent” 关键词。更可靠的路径是先把 LuminBuddy 的编辑部闭环做成可验证证据，再重写企业 Agent 版本。

## 四、LuminBuddy 编辑部方向应沉淀的证据

后续开发和使用过程中，建议持续记录：

- 一次完整内容任务如何被拆解；
- 人类分别把什么权限委派给研究、写作、审校和发布角色；
- Agent 之间传递的任务字段、产物格式和验收条件；
- 出现意见冲突时由谁裁决，依据是什么；
- 哪些行为必须人工确认；
- 单 Agent、固定流水线、多 Agent 三种模式的质量、耗时、token 和人工干预次数；
- 失败案例及修复前后的变化；
- 真实编辑或作者是否愿意持续使用，以及他们保留了哪些人工工作。

这些材料未来既是产品验证数据，也是简历、作品集和面试演示的共同事实底座。

## 五、当前事实台账中的主要待确认项

| 事实簇 | 当前出现的口径 | 处理方式 |
|---|---|---|
| LuminBuddy 用户与内容结果 | 53 名用户；3 名真实作者；7 篇采用；60 次提交/25 次采用 | 解释四组数字的包含关系、时间范围和数据来源 |
| 使用规模 | 1000+ 或 2000+ 模型调用；200+ 访问 | 查日志或截图，确认统计周期与是否去重 |
| 质量评测 | 9 个场景、100% 通过 | 改为准确的任务/用例描述，并保留失败分布 |
| 自动修复 | 6 次触发、6 次成功、2 次失败等互相矛盾表述 | 修复统计逻辑后重新跑评测 |
| 成本 | 单次约 0.0031 元 | 标注模型、价格、token 口径和日期，或暂不使用 |
| 采用率变化 | 约提升 35% | 明确基线、样本、计算方式及因果边界 |
| HearHer 样本与完成度 | 多组歌曲数、场景数、完成度 | 以最终评测数据和团队材料为准，解释口径差异 |
| 自动化测试 | 87/87 | 对应到具体版本、测试类型和可复现结果 |

## 六、发布前检查

每份简历导出前，用以下问题快速审查：

- 招聘方能否在十秒内看懂目标角色？
- 前半页是否放了与岗位最相关、最强且最可信的证据？
- 每个项目是否先说用户与问题，再说技术？
- 是否清楚区分个人项目、团队项目和本人职责？
- 所有数字是否能解释分母、时间、来源和限制？
- 是否存在从旧版本继承但已经失效的数字或技术描述？
- 是否把 Demo/MVP 写成了生产落地？
- 每项核心能力是否至少有一个具体行为作证？
- 是否存在无法在面试中展开三层追问的句子？
- PDF、公开作品集和投递岗位是否一致？

## 七、下一次重构前只需要先回答三个问题

1. 当前主投方向是否正式收敛为“Agent 协作 / Agent 编辑部产品”，还是仍需要保留一个泛 AI 产品主版本？
2. LuminBuddy 的 53 名用户、3 名作者、7 篇采用文章、60 次提交与 25 次采用之间，准确的统计关系是什么？
3. 作品集公开下载的 WorkBuddy 定向简历，是有意作为当前门面，还是应该改成更中性的 Agent 产品版本？
